# 반복 일정 '이 날만 수정' — v4.5 설계

작성일: 2026-10-25 / 상태: 데이터·UI 구현 완료, 2026-10-26 내부 검토용 EXE 검증 완료 — 최신 증거는 [작업 기록](../../work/2026-10-25-v4.5-execution.md) 참조

## 사용자 결정

- v4.5에 포함한다. 한 회차의 본문·색상·시각·알림을 수정한다.
- 날짜 이동·반복 규칙·기간 변경은 한 회차 편집에서 제공하지 않는다.
- 반복 전체를 수정해도 기존 수정 회차의 본문·색상·시각·알림은 유지한다.
- 용어는 [CONTEXT.md](../../../CONTEXT.md)를 따른다. 기존 일정 계약은 [아키텍처](../../ARCHITECTURE.md)·[UI 계약](../../UI_PATTERNS.md)이다.

## 사용자에게 보이는 동작

예: 매주 월요일 09:00 '주간 회의'에서 11월 2일만 '현장 회의', 14:00, 다른 색, 30분 전 알림으로 바꾼다. 11월 2일은 바꾼 일정 하나만 표시·검색·알림에 쓰고, 나머지 월요일은 원래대로다. 이후 반복 전체를 10:00으로 바꿔도 11월 2일은 14:00이다.

- 반복 행의 우클릭은 `이 날만 수정` / `반복 전체 수정`, 구분선, `이 날만 삭제` / `반복 전체 삭제`다.
- 반복 행 더블클릭은 같은 두 편집 범위를 고르는 작은 메뉴를 먼저 연다. Esc·바깥 클릭은 쓰기 없이 취소한다. 선택 뒤 기존 인라인 편집기를 사용하고 편집 범위를 표시한다.
- 한 회차 편집은 색상·이모지·본문과 시각/알림을 제공한다. 시계 카드의 반복/기간은 표시하지 않는다. 전체 편집은 기존 반복/기간 계약을 유지한다.
- 수정 회차에는 `이 날만 수정됨` 표시/툴팁을 둔다. 저장 HTML·본문에 표식을 넣지 않는다.
- Enter/영역 밖 이동 저장, Esc 취소, 저장 실패 시 원본 유지·날짜/월 이동 및 종료 보류, 잠금·숨김 때 메뉴/예약 포커스 취소는 기존 계약을 따른다.
- 변경 없이 열었다 닫으면 예외 행을 만들거나 암호문을 다시 쓰지 않는다.
- 반복 전체 삭제는 그 원본에 속한 수정 회차도 삭제한다. 삭제 범위가 메뉴 이름과 일치해야 한다.

## 저장안: 기존 schedules에 수정 회차를 별도 행으로 연결

| 열 | 값 | 기존 행 기본값 |
|---|---|---|
| `series_id` | 수정 회차가 속한 반복 원본의 로컬 ID. 일반 일정/반복 원본은 NULL | NULL |
| `original_date` | 수정한 회차의 날짜, ISO 형식. 이번 범위에서는 행의 date와 같다 | 빈 문자열 |

- DB v19. `ALTER TABLE schedules ADD COLUMN` 두 개와 user_version 변경을 한 트랜잭션으로 수행한다. 기존 열·본문·salt·ID·설정은 읽어 재작성하지 않는다. 반복 원본·수정 회차의 본문은 모두 기존 `schedules.content` Fernet 경로를 사용한다.
- 한 원본/날짜당 수정 회차는 하나다. 생성/재편집은 `BEGIN IMMEDIATE` 안에서 기존 관계를 확인한 뒤 삽입/갱신한다. 별도 테이블·DROP/RECREATE·새 암호화 형식은 추가하지 않는다.
- 수정 회차는 본문·색상·시각·알림 전체의 스냅샷이다. 일부 필드만 원본을 동적으로 상속하지 않으므로 전체 변경이 사용자의 별도 편집을 덮어쓰지 않는다.
- 수정 회차의 반복·기간·repeat_until·repeat_skip은 비어 있다. 원본은 다른 수정 회차를 부모로 참조하지 못한다. 자기 참조·중복 날짜·날짜 불일치·끊긴 참조를 쓰기/Import에서 거부한다.
- 수정 회차 생성으로 원본의 `repeat_skip`을 바꾸지 않는다. 기존 500개 삭제 상한과 편집을 섞지 않으며, 조회 시 수정 회차 날짜의 원본 발생만 억제한다.
- 실패 시 원본과 수정 회차의 변경을 모두 롤백한다. 숨긴 원본·편집 전 내용으로 역덮어쓰지 않는다.

### 전체 변경·삭제 경계

- 원본의 본문·색상·시각·알림·반복 주기·종료일 변경은 수정 회차를 쓰지 않는다. 새 규칙에서 빠지거나 종료일 밖이 된 수정 회차도 원래 날짜에 남는다.
- 원본 반복을 끄는 경우: **사용자 확정(2026-10-25)**. 기존 수정 회차를 일반 일정으로 남기고 연결 정보만 해제한다. 본문·시각·알림·색상·ID는 보존한다. 원본 첫날과 수정 회차가 겹치면 둘 다 보일 수 있으므로 이 결과를 UI에서 안내한다.
- 수정 회차의 `이 날만 삭제`는 해당 행 제거와 원본 날짜 건너뛰기를 한 트랜잭션으로 수행해 원래 일정이 다시 나타나지 않게 한다. 기존 삭제 상한에 걸리면 둘 다 그대로 유지한다.
- 종료일이 있는 반복의 마지막 발생 자동 정리는 수정 회차까지 남아 있는지 확인한다. 수정 회차가 있으면 원본을 지우지 않는다.
- `반복 전체 삭제`는 원본 및 직접 연결된 수정 회차를 한 트랜잭션으로 삭제한다.

## 조회·검색·알림

- `get_schedules`·`get_occurrences`는 같은 읽기 snapshot에서 원본과 수정 회차를 읽고, 원본 발생을 날짜별로 대체한다. 반복 원본 자체가 조회 범위 밖이어도 해당 범위의 수정 회차는 표시한다.
- 반환값에는 실제 편집 행 ID와 반복 원본 ID, 회차 날짜, 수정 회차 여부를 구분한다. UI가 현재 선택 날짜로 저장 대상을 다시 계산하지 않는다.
- 달력 칩·개수·색·일정 목록은 동일한 펼친 결과를 사용한다. 수정 회차는 기간 막대가 아닌 하루 일정이다.
- 알림 조회는 알림을 끈 수정 회차도 먼저 확인해 해당 날짜 원본 알림을 억제해야 한다. 수정 회차 알림을 원본과 함께 두 번 울리지 않는다. 기존 12시간 확인 창·잠금·다시 알림 검증을 유지한다.
- 검색은 원본과 수정 회차를 각각 검색하며, 수정 회차에는 해당 날짜를 사용한다. 저장 행 기준 조회 함수는 삭제하지 않는다.

## Export·Import·시작 보호

- Export v4. 일정마다 파일 내 `source_id`, 수정 회차에는 `series_source_id`와 `original_date`를 담아 원본 관계를 표현한다. 로컬 ID를 다른 PC의 기존 ID에 직접 연결하지 않는다.
- Import는 v1/v2/v3를 계속 받는다(새 관계 없음). v4는 전체 타입·ID 유일성·부모 존재·자기/중첩 참조 금지·원본/날짜 유일성·수정 회차 옵션을 검증한 뒤 한 트랜잭션에서 원본 삽입 → 새 ID 매핑 → 수정 회차 삽입한다. 같은 파일을 두 번 가져오면 두 별도 묶음으로 추가하는 기존 정책을 유지한다.
- 기존 메모·바로가기·집중 세션 remap·위젯 상한·PIN/알림 처리 시각 제외 계약은 그대로다. 하나라도 실패하면 파일 전체 병합을 롤백한다.
- v18 데이터는 건강 검사·`calendar_pre_v19_v18.db` 보호 snapshot 성공 뒤에만 v19로 올린다. v17 이하에서 바로 올릴 때도 원래 버전의 보호본을 만든다. 기존 v17→v18 열 추가를 유지하고 새 단계의 원자성을 별도 검사한다.
- v4.4b 이하 EXE는 v19를 시작 건강 검사에서 차단한다. 기존 `.enc`는 v4.5에서 읽고, v4 파일은 구 EXE가 거부한다. 새 일정 관계를 구버전이 무시해 중복 알림/잘못된 삭제를 만들지 못하게 한다.
- 되돌리기는 보호 snapshot 시점까지만 가능하며 이후 입력분은 포함하지 않는다. 실행 중 DB/salt 교체 UI나 자동 삭제는 제공하지 않는다.
- 시작 건강 검사는 v19 관계 열 존재와 관계 구조를 확인하되, 원본의 현재 반복 규칙에서 빠진 수정 회차를 손상으로 오인하지 않는다. 기존 암호문·salt 전체 검사와 실패 시 무변경을 유지한다.

## 대안 검토

- `repeat_skip` + 연결 없는 일반 일정: 초기 변경은 작지만 전체 삭제·재편집·Import에서 관계를 복원할 수 없어 사용자 요구를 안정적으로 지키기 어렵다.
- 암호화 JSON 예외 목록을 원본 열에 저장: ID 매핑은 간단하지만 한 회차 수정마다 예외 전체 재암호화, 건강 검사/레거시 암호화 변경, 검색/내보내기의 새로운 중첩 본문 형식이 필요하다.
- 연결된 별도 행은 두 메타데이터 열과 Export 관계 처리가 필요하지만 본문 암호화·검사·일반 일정 저장 경로를 유지한다. 현재 제약에서는 이 안을 권장한다.

## 구현·검증 순서

1. 확정한 동작에 맞춰 설계를 검토한 뒤 규칙/API·v19·Export v4를 구현한다. UI 전에 합성 v18/17 migration 원본 열·salt 보존, 중간 실패 롤백·멱등성을 검사한다.
2. 같은 날 대체, 다중 회차, 전체 수정 보존, 종료일/주기 변경, 한 회차/전체 삭제, 알림 끔 대체, 재시작·Import 왕복/ID 충돌/잘못된 관계 거부를 검증한다.
3. 인라인 편집 범위·색상·시계 카드·메뉴 수명을 연결하고 세 크기와 100/125/150% 배율·한글/이모지·Undo·저장 실패·잠금/숨김을 검사한다.
4. 데이터 변경은 `data`, 관련 UI는 `quick --tests`, 하네스/격리 입력 변경은 `full`로 검사한다. release 직전에 같은 입력의 full을 의무 중복하지 않는다.
5. release smoke에 합성 수정 회차와 v18→v19 시나리오를 추가하고 기존 v17 업그레이드 시나리오도 유지한다. 구 EXE의 v19 차단과 보호 snapshot 되돌리기는 합성 사본에서 별도로 확인한다.

## 현재 상태

DB v19·Export v4·반복 회차 데이터/UI 코드를 구현했다. 실사용 데이터는 변경하지 않았으며 전체 3,095개 테스트·EXE 빌드·격리 5개 시나리오를 통과했다. 실제 수동 확인·공개 배포는 별도다. 최신 구현/검증/미실행 범위는 실행 기록의 2026-10-26 재개 이후 기록을 따른다. 알림 시계 보정은 [실행 기록](../../work/2026-10-25-v4.5-execution.md)의 독립 단계다.
