# 공휴일 데이터 최신화와 만료 안내 설계

- 작성일: 2026-10-20
- 상태: 설계 (구현 전)
- 관련: `fetch_data.py`, `holidays.py`, `tools/verify.py`, `main.py`, `app_info.py`, `ui_date_time_calculator.py`

## 배경과 이유

기후노트는 공무원 내부망 PC용 오프라인 앱이다. 앱이 공공데이터포털 API를 직접 부를 수 없으므로,
공휴일·음력은 개발 PC에서 `fetch_data.py`로 받아 `holidays.py`(git 추적)에 넣고 EXE에 함께 묶는다.

지금은 개발자가 버전업 때 API를 다시 돌리는 일을 기억해야 한다. 잊으면 새 연도 공휴일이나
새로 지정된 임시공휴일이 빠진 EXE가 나가고, 사용자는 그 날을 평일로 본다.
또 `fetch_data.py`는 API 오류를 조용히 빈 결과로 바꿔 덮어쓰기 때문에, 다시 돌려도 일부가 빠질 수 있다.

개발자가 더 이상 업데이트하지 못하는 상황(퇴직·부재 등)도 대비해야 한다.
그때 직원이 데이터가 끝났다는 것을 알고 개발자에게 연락할 수 있어야 한다.

## 목표

1. release를 할 때마다 공휴일 데이터가 자동으로 API 최신 값이 된다. 개발자가 따로 챙기지 않아도 된다.
2. API 오류·일부 누락 때문에 공휴일이 빠진 데이터가 저장되거나 EXE로 나가지 않는다.
3. 같은 날 공휴일이 두 개면 두 이름을 모두 보여준다.
4. 공휴일 데이터가 끝나 갈 때와 끝난 뒤, 직원이 개발자 메일 주소를 안내받는다.

## 하지 않는 것

- 앱(EXE)이 인터넷에서 직접 받아 오는 기능. 런타임은 오프라인 전용을 유지한다.
- 공휴일 날짜를 코드로 계산·추정해 채우는 것. 검사는 "이름이 있는지"만 본다.
- 음력 데이터 갱신 방식 변경. 음력은 2025–2050년이 이미 있어 release 때 다시 받지 않는다.
- DB 스키마, 설정 키, Export 형식, salt 변경.
- quick / data / full / doctor 검사에 네트워크 사용 추가.
- 앱 표시 버전(`app_info.APP_VERSION`) 변경. 이 작업은 다음 release 버전에 함께 들어간다.

## 실패로 보는 경우 (기능은 돌아가도 실패)

- API 일부 실패나 키 오류인데도 `holidays.py`가 바뀌거나 release가 계속된다.
- 기존 공휴일이 사라지거나 이름이 바뀌었는데 사람 확인 없이 EXE에 들어간다.
- 어떤 연도에 일부 공휴일만 들어와, 앱이 그 해를 "자료 있음"으로 판단한다
  (만료 안내가 1년 늦춰지고 근무일 계산이 틀린다).
- API 키가 화면 출력·로그·`report.json`·`summary.md`·예외 메시지에 남는다.
- quick / data / full이나 pytest가 네트워크나 API 키를 요구하게 된다
  (동료는 키 없이 클론·테스트·빌드할 수 있어야 한다는 기존 결정).

## 현재 상태 (사실)

- `holidays.py`: `KOREAN_HOLIDAYS` 2025–2027년, `LUNAR_MAPPING` 2025–2050년.
  함수 `get_lunar_date`, `get_holiday`, `is_holiday`, `holiday_last_year`.
  키가 날짜라서 2025-05-05는 "부처님오신날"만 남고 "어린이날"이 빠져 있다.
- `fetch_data.py`
  - `fetch_holidays` / `fetch_lunar_month`는 예외가 나면 `[]`를 돌려준다.
    응답의 결과 코드는 보지 않는다(키 오류 응답도 "0건"으로 처리됨).
  - `main()`은 백업·검증 없이 `holidays.py`를 바로 덮어쓴다.
    공휴일은 한 해 전체가 0건일 때만 그 해를 건너뛴다(한 달 실패는 그대로 저장).
  - `verify_holiday_data()`는 최대 연도(공휴일 ≥2027, 음력 ≥2050)와 공휴일 40건 이상만 본다. `main()`에서 호출하지 않는다.
  - HTTPS 전용 opener, `defusedxml`, `.env`의 `LUNAR_API_KEY`를 쓴다.
- 만료 안내: `main.py` 288–300행. `holiday_last_year()`의 마지막 연도 12월부터, 또는 그 다음 해부터
  앱 시작 2초 뒤 `InfoBar.warning`을 10초 동안 띄운다.
  문구는 "공휴일은 {Y}년 데이터까지 제공됩니다. 이후 데이터는 패치를 통해 업데이트해 주세요."
  마지막 연도는 데이터에서 계산하므로, 데이터가 늘면 안내 시점도 자동으로 늦춰진다.
- 사용처: `ui_main.py`(달력 빨강·음력·공휴일명), `ui_schedule_options.py`(카드 달력 색),
  `date_time_calculator.py`(근무일 공휴일 제외, 자료 없는 연도는 계산 보류).
- `tools/verify.py release`: doctor → `inputs_before` 스냅샷 → 전체 pytest → PyInstaller 빌드 → 격리 EXE 실행.
  마지막에 `inputs_after`와 비교해 다르면 실패한다. 종료 코드는 데이터·산출물 검증 실패 1(`VerificationFailure`),
  환경 오류 2.
- release는 개발자 PC(이 PC)에서 PowerShell로 돌린다. 이 PC에는 `.env`(API 키)와 인터넷이 있다.
- v4.4 파일 변환은 `0c7e833`으로 커밋되어 있다. `main.py`, `app_info.py`는 작업 트리 변경이 없다.
- 날짜·시간 계산기 화면과 시험 일부가 공휴일 범위를 2025–2027로 박아 두었다.
  `ui_date_time_calculator.py` 347·348·588행의 문구, `tests/test_date_time_calculator.py` 162·166행,
  `tests/test_ui_date_time_calculator.py` 192–195행. 계산 자체(`date_time_calculator.HOLIDAY_RANGE`)는 데이터에서 범위를 구한다.

## 결정 사항

### 1. `fetch_data.py` 보강 (수동 실행과 release가 같이 쓰는 부분)

**받기 실패의 정의.** 다음 중 하나라도 해당하면 그 요청은 실패다.
- 네트워크·HTTP 오류, 시간 초과
- XML 파싱 실패, 안전하지 않은 XML(`defusedxml` 거부)
- 응답의 결과 코드(`header/resultCode`)가 `00`이 아니거나 없다
  (키 오류 응답 `OpenAPI_ServiceResponse` 형식도 여기서 실패로 걸린다)
- `totalCount`보다 받은 `item` 수가 적다
- 필요한 필드(`locdate`, `dateName`, 음력의 `solYear`·`solMonth`·`solDay`·`lunMonth`·`lunDay`)가 없거나 형식이 틀리다

정상 결과 코드에 `totalCount` 0인 응답은 실패가 아니다(아직 발표되지 않은 연도).
공공데이터포털 공통 코드 `03`(NODATA_ERROR)도 같은 "자료 없음"으로 본다(설계자 판단).
빈 연도의 실제 응답 형식은 구현 중 이 PC의 첫 실제 호출에서 확인해 작업 기록에 남긴다.

**실패 처리.** 한 요청이라도 실패하면 전체를 중단하고 `holidays.py`를 바꾸지 않는다. 어느 연·월·서비스에서
실패했는지 알려 주고 비영 종료한다. 부분 결과로 저장하지 않는다.

**실패 종류와 종료 코드 (설계자 판단).** 하네스의 기존 구분(1 = 데이터·산출물 문제, 2 = 환경 문제)을 따른다.
- 2(환경): 키 없음, 네트워크·HTTP 오류·시간 초과, 결과 코드가 `00`·`03`이 아닌 응답
  (키 미등록·호출 한도 초과·접근 거부·서비스 오류 등, 키 오류 `OpenAPI_ServiceResponse` 포함)
- 1(데이터): XML 파싱 실패·안전하지 않은 XML, `totalCount` 대비 항목 부족, 필드 누락·형식 오류,
  검증 실패, release 비교의 삭제·이름 변경
- 수동 `python fetch_data.py`는 종료 코드 구분 없이 비영 종료하면 된다.

**새 연도가 일부만 들어온 경우 (설계자 판단).** 지금 `holidays.py`에 없는 새 연도가 핵심 이름 8개(아래 검증)를
다 갖추지 못했으면 그 연도는 통째로 넣지 않고 "제외한 연도"로 보고한 뒤 계속한다. 선거일·임시공휴일만 먼저
발표된 해 때문에 release가 몇 달씩 막히지 않게 하면서, 앱이 그 해를 "자료 있음"으로 오인하지 않게 하기 위해서다.
이미 `holidays.py`에 있는 연도가 핵심 이름을 잃으면 제외하지 않고 실패로 멈춘다. 수동 실행과 release 모두 같은 규칙이다.

**같은 날 공휴일 이름 합치기.** 같은 날짜에 `isHoliday == "Y"` 항목이 둘 이상이면 API 응답 순서대로,
같은 이름은 한 번만, `·`로 이어 붙인다. 예: `"2025-05-05": "어린이날·부처님오신날"`(실제 순서는 API를 따른다).

**데이터 검증 강화.** `verify_holiday_data()`에 기존 조건과 함께 다음을 더한다.
- `KOREAN_HOLIDAYS`의 모든 연도에 핵심 이름 8개가 각각 어떤 공휴일 이름 안에 들어 있어야 한다:
  `1월1일`, `삼일절`, `광복절`, `개천절`, `한글날`, `기독탄신일`, `설날`, `추석`.
  합친 이름(예: `어린이날·부처님오신날`) 안에 들어 있어도 인정한다. 날짜는 보지 않는다.
- 현재 번들 데이터(2025–2027)는 이 검사를 통과한다(확인함).

**저장 절차.** 임시 파일에 새 `holidays.py`를 쓴다 → 그 파일을 모듈로 읽어 `verify_holiday_data()`를 통과하는지
확인한다 → 기존 `holidays.py`를 백업한다 → 원자적으로 교체한다(`os.replace`). 검증 실패 시 임시 파일만 지우고 원본은 그대로 둔다.
백업 위치는 git 추적 밖이어야 한다. 수동 실행은 `output/holiday-refresh/<YYYYMMDD-HHMMSS>/holidays.py`,
release는 그 실행의 `output/harness/<run-id>/` 안이다(구현자 재량으로 이름은 바꿔도 된다).

**생성 파일 형식.** 변수 이름, 함수 4개, 머리 주석, 정렬 순서는 지금과 같게 유지한다. 바뀌는 것은 데이터와 합친 이름뿐이다.

**수동 실행(`python fetch_data.py`).** 지금처럼 음력과 공휴일을 모두 다시 받아 전체를 만든다.
release가 막은 "삭제·이름 변경"을 사람이 확인하고 받아들이는 공식 경로가 이것이다.

**API 키.** 키는 화면 출력·로그·보고서·예외 메시지에 남기지 않는다. 요청 URL이나 urllib 오류 문자열을 그대로 출력하지 않는다.

### 2. release 시작 때 공휴일 최신화

`tools/verify.py release`에만 단계를 추가한다. 다른 프로필은 바꾸지 않는다.

**순서.** 실행 폴더 생성 → doctor → **공휴일 최신화** → `inputs_before` 스냅샷 → pytest → 빌드 → 격리 실행.
스냅샷 전에 끝나야 `inputs_after` 비교와 충돌하지 않고, 바뀐 데이터로 테스트와 빌드가 돈다.

**받는 범위.** 공휴일만 받는다. 범위는 `fetch_data.py`와 같은 2025–2050년이다.
음력은 받지 않고 지금 `holidays.py`의 `LUNAR_MAPPING`을 그대로 유지한다.
받기 실패 정의·이름 합치기·검증은 1번과 같은 코드를 쓴다.

**비교와 처리.** 새로 받은 공휴일과 지금 `holidays.py`의 `KOREAN_HOLIDAYS`를 날짜 기준으로 비교한다.

| 결과 | 처리 |
|---|---|
| 같다 | `holidays.py`를 건드리지 않고 계속한다. 보고서에 "공휴일 최신 확인"과 조회 시각을 남긴다. |
| 추가만 있다 | 1번 저장 절차로 `holidays.py`를 바꾸고 계속한다. 추가된 날짜·이름을 화면과 보고서에 남긴다. |
| 삭제나 이름 변경이 하나라도 있다 | `holidays.py`를 바꾸지 않고 멈춘다(종료 코드 1). 삭제·변경·추가 목록을 모두 보여주고, 확인 뒤 `python fetch_data.py`를 실행하고 다시 release하라고 안내한다. |
| 받기 실패·검증 실패 | `holidays.py`를 바꾸지 않고 멈춘다. 종료 코드는 1번의 "실패 종류와 종료 코드"를 따른다. |

일부만 들어온 새 연도는 1번 규칙대로 제외하고 보고하며, "추가"로 세지 않는다.
doctor가 오류를 내면 공휴일 단계도 실행하지 않는다(기존처럼 환경 오류로 끝남).

우회 옵션(검사 건너뛰기)은 두지 않는다. (설계자 판단: "매 release마다 최신화"라는 요구를 그대로 따름)

**뒤 단계가 실패한 경우 (설계자 판단).** 공휴일을 갱신한 뒤 pytest·빌드·격리 실행이 실패해도 갱신한 `holidays.py`는
되돌리지 않는다. 검증을 통과한 실제 API 값이고, 다음 release도 같은 데이터로 pytest를 다시 거치기 때문이다.
보고서에는 "공휴일 갱신됨"이 그대로 남는다.

**보고.** 기존 `result.json`에 공휴일 단계 결과(상태, 추가·삭제·변경·제외 연도 목록, 조회 시각, 받은 연도 범위)를 남기고
`summary.md`에 한 블록으로 보인다. 키는 남기지 않는다.

**커밋.** release는 바뀐 `holidays.py`를 커밋하지 않는다. 개발자가 release 기록과 함께 커밋한다.
`source_snapshot`은 이미 작업 트리의 변경(dirty)을 기록하므로 추가 처리는 필요 없다.

**첫 release 예상.** 이름 합치기를 넣은 뒤 첫 release는 2025-05-05 이름이 바뀌어 한 번 멈출 것으로 예상된다.
그때 `python fetch_data.py`를 직접 실행해 받아들이면 된다.

### 3. 만료 안내 문구

시점·방식은 그대로다: `holiday_last_year()`의 마지막 연도 12월부터, 또는 그 다음 해부터, 앱 시작 2초 뒤
`InfoBar.warning`, 위쪽, 10초.

문구는 두 단계로 나눈다. `{Y}`는 마지막 연도, `{email}`은 개발자 메일이다.

- 마지막 연도 12월
  - 제목: `공휴일 안내`
  - 내용: `공휴일 정보는 {Y}년까지 들어 있습니다.\n새 버전을 받지 못했다면 개발자({email})에게 메일로 알려 주세요.`
- 그 다음 해부터
  - 제목: `공휴일 안내`
  - 내용: `{Y+1}년부터는 달력에 공휴일이 표시되지 않습니다.\n개발자({email})에게 메일로 알려 주세요.`

**메일 주소의 정본.** `app_info.py`에 `APP_CONTACT_EMAIL = "ggjo@korea.kr"`를 두고,
`APP_AUTHOR`는 이 상수로 지금과 똑같은 문자열(`기후에너지환경부 보문산불주먹 (ggjo@korea.kr)`)을 만든다.
설정 화면 등 기존 `APP_AUTHOR` 표시는 바뀌지 않아야 한다.

**시험 가능하게.** 오늘 날짜·마지막 연도·메일을 받아 (제목, 내용) 또는 "안내 없음"을 돌려주는 Qt 없는 함수로 문구를 만들고,
`main.py`는 그 결과만 `InfoBar`에 넘긴다. 함수 위치는 구현자 재량이다.

**표시 확인.** 기본 크기(가장 좁은 메인 창)에서 메일 주소가 잘리지 않고 보이는지 확인한다.
잘리면 줄바꿈 위치나 InfoBar 폭을 조정한다(문구 뜻은 유지).

### 4. 공휴일 범위 표기를 데이터에서 가져오기 (설계자 판단)

2028년이 처음 추가되는 release는 이 기능이 자동화하려는 정상 경로다. 그때 박아 둔 2025–2027 때문에
시험이 실패하거나 EXE 화면이 틀린 범위를 보이면 안 된다.
- `ui_date_time_calculator.py`의 공휴일 범위 문구 3곳(347·348·588행)은 `date_time_calculator.HOLIDAY_RANGE`
  (또는 같은 데이터에서 구한 값)로 만든다. 문구 형식(`2025–2027년`, 괄호 안 `2025–2027`)은 지금과 같게 유지한다.
- `tests/test_date_time_calculator.py`, `tests/test_ui_date_time_calculator.py`의 범위 관련 시험은
  `HOLIDAY_YEARS`의 최소·최대 연도와 그 다음 해로 기대값을 만든다(연도 숫자를 박지 않는다).
- 문구 길이는 연도 숫자만 바뀌므로 창 폭 영향은 없을 것으로 보지만, 기존 날짜·시간 계산기 배치 시험으로 확인한다.

## 시험

`tests/test_fetch_data.py` 확장
- 결과 코드 오류·키 오류 형식 응답·`totalCount` 불일치·필드 누락이 실패로 처리된다.
- 정상 코드 + 0건 응답과 `03` 응답은 실패가 아니다.
- 실패 종류별 종료 코드(환경 2 / 데이터 1)가 위 표와 맞다.
- 핵심 이름이 모자란 새 연도는 제외·보고되고, 기존 연도가 핵심 이름을 잃으면 실패한다.
- 한 달이라도 실패하면 `holidays.py`(시험용 임시 경로)가 바뀌지 않는다.
- 같은 날 두 공휴일 이름이 응답 순서대로 `·`로 합쳐지고, 같은 이름은 한 번만 들어간다.
- 핵심 이름 하나가 빠진 연도가 있으면 검증이 실패하고, 합친 이름 안의 핵심 이름은 인정된다.
- 현재 번들 데이터는 강화된 검증을 통과한다.
- 교체 시 백업이 만들어지고, 검증 실패 시 원본이 그대로다.
- 출력·예외 문자열에 가짜 키가 나타나지 않는다.

release 공휴일 단계(가짜 받기 함수 사용)
- 같다 / 추가만 / 삭제 / 이름 변경 / 받기 실패 / 키 없음 각각의 처리·종료 코드·보고서 기록.
- 단계가 `inputs_before` 스냅샷보다 먼저 실행된다.
- 음력 매핑은 바뀌지 않는다.
- 보고서에 키가 나타나지 않는다.

만료 안내
- 마지막 연도 11월 → 안내 없음, 마지막 연도 12월 → 1단계 문구, 다음 해 → 2단계 문구.
- 메일 주소가 `app_info.APP_CONTACT_EMAIL`에서 오고, `APP_AUTHOR` 문자열이 그대로다.

범위 표기
- 날짜·시간 계산기 화면 문구와 오류 문구가 데이터의 최소·최대 연도를 따른다.
  가짜로 마지막 연도를 늘린 데이터에서도 시험이 통과한다(2028 추가 release를 흉내).

회귀
- 기존 공휴일 표시(`test_ui.py`의 공휴일 빨강 등), 날짜·시간 계산기 시험이 계속 통과한다.
