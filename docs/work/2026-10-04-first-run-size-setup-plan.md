# 작업 기록: 최초 실행 크기 선택 — A안 구현

작성일: 2026-10-04 / 상태: A안 구현·최종 release 통과, 커밋·EXE 배치·로컬 초기화 진행

## 사용자 요청 반영 — 실행 계획 확정 범위

2026-10-04 최신 요청: A안 구현, 버전 그대로 유지, AGENTS.md 업데이트와 커밋은 유지한다. 그 이후 이 PC의 DB를 전체 초기화하여 완전히 신규 설치 상태에서 사용자가 직접 시작한다. 이전의 ‘크기만 초기화·다른 앱 데이터 유지’ 요청은 이 PC의 초기화 범위에 한해 대체됐다. 계획 승인 후 ‘구현하자’ 요청으로 아래 실행 범위가 승인됐다. 하단 최초 계획/시안 결과는 당시 기록이며 제품 구현 결과를 마지막에 추가한다.

실행 순서는 다음과 같다.

1. A안 최초 크기 선택을 Qt로 구현한다. `app_info.py`의 v3.8d·출시일·Windows 버전과 DB v17·Export v2·Qt/lock을 유지한다.
2. 신규 설치 자동 표시와 기존 사용자 생략을 구현한다. 크기 재선택 예약 파일이나 테스트용 우회 진입 기능은 추가하지 않는다. 일반 기존 사용자가 업데이트만으로 설정 창을 보게 하지 않는다.
3. AGENTS.md의 해당 기능 계약과 관련 정본 문서·작업 기록을 갱신해 최종 검증 입력에 포함한다. 기존 사용자 변경은 그대로 보존한다.
4. 관련 자동 검사·100/125/150% 합성 배율·작은 작업 영역을 확인한다. 같은 이름의 새 EXE를 PowerShell `release`로 빌드하고 격리 데이터에서 검증한다. `release`에 포함된 전체 검사를 별도 `full`로 중복 실행하지 않는다. 실제 회사 KVM 등은 미확인으로 구분한다. 검증 후에는 결과 기록만 보완하고 이번 작업 부분만 스테이징해 로컬 커밋한다. 기존 보안·과거 릴리스 문서 수정과 미추적 자료를 함께 커밋하지 않는다. push는 하지 않는다.
5. 검증한 새 EXE를 `dist/기후노트_v3.8d.exe`에 배치한다. 같은 이름의 이전 파일은 별도 보존하고 포함 코드·Qt DLL·SHA-256을 대조한다. 실제 실행 중인 EXE를 강제로 교체하거나 종료하지 않는다.
6. 커밋과 새 EXE 준비가 끝난 뒤에만, 아래 절차로 이 PC를 신규 설치 상태로 초기화한다. 이후 앱을 자동 실행하거나 설정을 대신 확정하지 않고, 사용자가 새 EXE를 열어 A안부터 직접 시작할 수 있게 남긴다.

### 이 PC를 완전히 신규 설치 상태로 준비하는 방법

DB만 지우면 기존 `.salt`, WAL/SHM 또는 `backups/calendar_*` 때문에 건강 검사가 `incomplete_dataset`으로 차단한다. 앱의 기존 Factory Reset도 빈 DB와 새 salt를 즉시 만들므로 ‘DB가 아직 없는 최초 실행’과는 다르다. 이번 사용자의 확인 목적에는 **활성 데이터 폴더를 비우되 기존 데이터셋은 폴더째 외부 보존**하는 방식이 맞는다.

- 대상은 `%LOCALAPPDATA%/MyDesktopCalendar` 앱 데이터 폴더다. 정상 종료의 최신 일정·스티키 저장이 성공하고 앱 프로세스와 파일 사용이 끝난 것을 확인한 후 진행한다. 저장 실패나 실행 중에는 초기화하지 않으며 강제 종료하지 않는다.
- 현재 데이터 폴더의 DB·원본 salt·WAL/SHM·기존 백업·로그 등을 함께 날짜와 고유값을 붙인 **형제 폴더** `%LOCALAPPDATA%/MyDesktopCalendar.before-first-setup-<시각-고유값>`로 보존한다. 보존 위치는 기존 활성 폴더 밖에 둔다. 기존 백업을 회전 삭제하거나 암호문과 salt를 분리하지 않는다.
- 실제 작업 전 원본·목적지의 해석된 절대 경로를 확인한다. 원본이 명시한 앱 데이터 폴더인지, 목적지가 같은 사용자 LocalAppData 아래의 충돌 없는 새 보존 폴더인지 검증하며 기존 폴더에 덮어쓰지 않는다. 재분석 지점 등 경로가 예상과 다르면 중단한다.
- 정상 종료 후 파일 목록·크기·SHA-256을 기록하고 같은 볼륨의 폴더 이름 변경/이동으로 보존한다. 보존 후 동일성을 대조하고 실패하면 신규 시작 준비를 완료로 보고하지 않는다. 이동 전후 파일과 원본 salt를 그대로 유지하는 가역적 보존이며 파일을 개별 삭제하지 않는다.
- 활성 경로에는 DB·salt·WAL/SHM·기존 백업이 없는 상태를 남긴다. 빈 DB나 새 salt를 미리 생성하지 않는다. 새 EXE를 사용자가 실행하면 기존 `fresh` 판정으로 A안이 뜨고 선택 확정 후 신규 데이터셋을 생성한다.
- 초기화 범위는 앱 내부의 **일정·메모·휴지통 스티키·D-Day·집중 기록·바로가기 등록·크기·위치·모니터·PIN을 포함한 모든 DB 설정**이다. 이전 내용은 새 앱에 나타나지 않고 별도 보존 폴더에만 남는다.
- 연결된 원본 파일·폴더, 변환한 HWP/HWPX 결과물, 프로젝트 소스·Git·venv·다른 앱 데이터·Windows 시작프로그램 등록 등 앱 데이터 폴더 밖의 항목은 초기화 대상이 아니다. 앱 정상 실행이 수행하는 기존 동작은 별도다.
- 보존 경로와 결과만 사용자에게 알려주며 일정 본문·PIN·파일 경로 등 내용은 보고서에 출력하지 않는다. 파일 목록을 포함한 로컬 증거는 Git·배포 대상에 포함하지 않는다.
- 제품 회귀/EXE 자동 검사는 계속 합성 데이터에서만 한다. 마지막 단계는 사용자가 명시한 실제 앱 데이터 초기화이며 실사용 데이터를 회귀 테스트 입력으로 사용하지 않는다.

## 결정과 진행

### 현재 코드에서 확인한 근거

- `database.inspect_startup_data_health()`는 DB가 없고 salt·WAL/SHM·기존 백업도 없을 때만 `ok=True, code="fresh"`를 반환한다. DB가 없어도 복구해야 할 파일이 남아 있으면 `incomplete_dataset`으로 차단한다.
- `main._initialize_database()`는 건강 검사 → 보호백업 → 마이그레이션 → 일일 백업을 수행하고, 이후 `MainCalendarWindow`를 만든다.
- `ui_settings.SettingsWindow._on_scale_changed()`는 `calendar_scale`을 즉시 저장한다. 메인은 시작할 때 이 키를 읽는다.
- 기존 값은 `compact`/`medium`/`large`, 기본값은 `compact`다. DB가 비어 있다는 이유나 키가 없다는 이유로 신규 사용자를 추측하면 안 된다.
- ‘최초’는 현재 PC·계정의 데이터 폴더를 기준으로 한다. EXE를 다른 폴더로 이동하거나 업데이트했다고 다시 표시하지 않는다.
- 기준 문서: [아키텍처](../ARCHITECTURE.md), [UI 계약](../UI_PATTERNS.md), [보안 코딩](../CODING_STANDARDS.md), [검증](../TESTING.md).

### 제안하는 시작 흐름

1. 단일 인스턴스 잠금, QApplication·폰트·테마를 준비한다. HWP worker 조기 분기는 그대로 유지한다.
2. 기존 read-only 건강 검사를 수행한다. 실패하면 지금과 같은 데이터 보호 오류로 중단한다.
3. `fresh`일 때만 메인/트레이 생성 및 DB·salt·백업 생성보다 먼저 독립 최초 설정 대화상자를 연다. 기본 선택은 `compact`다.
4. 선택 중에는 메모리에서 미리보기만 바꾼다. DB는 쓰지 않는다.
5. X·Esc·종료는 앱을 종료한다. 아직 DB·salt·백업을 만들지 않았으므로 다음 실행에도 설정 창이 나온다. 기존 시작 단계의 로그·잠금 파일은 이 판정과 별개다.
6. ‘이 크기로 시작’은 선택을 확정하고 신규 DB 초기화를 진행한다. `migrate()`의 신규 DB 초기 설정 경로에 선택값을 넘겨, 기존 `calendar_scale` 키가 처음 생성될 때 그 값을 넣는다. 이후의 `INSERT OR IGNORE`는 이를 보존하도록 한다. 기존 DB 마이그레이션과 `reset_database()` 호출에는 이 인자를 전달하지 않는다.
7. 선택값이 저장된 상태로 최초 검증 백업을 만든다. 초기화/저장/백업 실패는 메인 진입을 차단하고 원본과 오류 근거를 보존한다. 일부 초기화된 DB를 지워서 ‘fresh’로 만드는 복구는 금지한다.
8. 정상 완료 후 메인을 한 번 생성한다. 기본 크기 창을 잠깐 띄운 뒤 선택 크기로 바꾸는 깜박임을 만들지 않는다.

새 `setup_completed` 설정 키나 스키마 변경은 제안하지 않는다. 크기 선택을 DB 생성 전에 완료하므로 정상 초기화 이후에는 기존 DB 유무와 건강 검사 결과만으로 첫 설정을 건너뛸 수 있다. 진행 중 강제 종료/전원 차단으로 불완전 데이터셋이 생기면 기존 건강 검사·복구 정책을 따르며, 설정 창 반복을 위해 데이터셋을 자동 삭제하지 않는다.

### 동작 범위

| 상황 | 제안 동작 |
|---|---|
| 실제 신규 설치 | 크기 선택 창 표시 |
| 기존 사용자 업데이트 / 일정이 하나도 없는 기존 DB | 표시하지 않고 기존 크기 유지 |
| 새 설정 창에서 선택만 변경 | 메모리 미리보기만 변경 |
| 시작 확정 | 선택한 모드로 첫 화면 표시, 이후 재실행에도 유지 |
| 시작 전 X·Esc·종료 | DB 생성 없이 종료, 다음 실행에서 다시 선택 |
| DB 손상 또는 salt/백업만 남은 상태 | 기존 데이터 보호 오류. 최초 설정으로 우회하지 않음 |
| Factory Reset | 기존 초기화 동작 유지, 최초 설정 자동 재표시 없음 |
| Export/Import | 기존 크기 설정 왕복 유지, 별도 최초 설정 플래그 없음 |
| HWP 변환 작업 프로세스 | 최초 설정·일반 앱 초기화에 진입하지 않음 |

### 화면 제안

- 선택: 기본 ‘작게 띄워두기’, 중간 ‘일정도 함께 보기’, 크게 ‘위젯까지 한눈에’.

- 세 모드에서 제공되는 기능은 동일하고, 크기에 따라 일정·위젯의 배치가 달라진다. ‘크게’에서만 위젯을 사용할 수 있다는 의미로 설명하지 않는다.
- 시작 버튼은 확정용 한 개, 종료는 보조 동작이다. 제품 구현에서는 저장 중 중복 클릭을 막고 실패를 명확히 알린다.
- 키보드: Tab, 선택 항목의 방향키/Space, 시작의 Enter, 종료의 Esc. 작은 화면·100/125/150% 배율에서 설명을 줄이거나 세로 배치로 전환해 전체 버튼을 유지한다.
- 시안의 시작/종료는 로컬 화면 전환만 한다. 실제 앱·DB를 제어하지 않는다.

### 구현 순서와 예상 변경 파일

1. `ui_first_run.py` 신규: DB 접근 없는 선택 대화상자. 선택값 또는 취소 결과를 반환한다. 미리보기를 위해 실제 메인 창을 만들지 않는다.
2. `main.py`: 기존 건강 검사 결과를 이용해 신규 분기를 삽입한다. 정상 메인 진입은 초기화와 백업 성공 이후다. 기존 `_initialize_database()` 호출자와 테스트 호환을 확인한다.
3. `database.py`: 신규 생성에서만 선택한 `calendar_scale`을 초기 설정에 넣는 좁은 변경. 입력은 세 값만 허용하며 기존 DB 값은 덮어쓰지 않는다. 스키마 v17·Export v2·salt·기존 본문·6슬롯을 유지한다.
4. 관련 테스트 추가: 신규 설정 표시/생략/취소, 세 크기 첫 화면과 재실행, 입력값 검증, 기존 데이터 보존, 초기화·Import, worker 분기. 검사에는 합성 데이터만 사용한다.
5. `tools/smoke_release.py`: 현재 신규 설치 smoke는 자동 메인 진입을 기대하므로 새 설정 창에서 명시적으로 크기를 선택하는 절차를 반영한다. 제품에 setup 우회 환경변수를 추가하지 않는다. 기존 데이터·손상 데이터 시나리오는 설정 창이 없는 것도 검사한다.
6. 구현 확정 후 `docs/UI_PATTERNS.md`, `docs/ARCHITECTURE.md`, `docs/TESTING.md`에 영구 계약과 신규 실행 흐름을 반영한다. 기존 변경 중인 AGENTS.md/릴리스 문서는 충돌 없이 필요한 부분만 갱신한다.

## 제품 구현과 실제 검증

- `ui_first_run.py`: A안 3개 선택 카드·벡터 화면 도식·선택 설명·시작/종료. 최초 기본 선택, 키보드 방향키/Space/Enter/Esc와 Tab, 시스템 테마, 좁은 화면 세로 배치·짧은 화면 여백 축소를 적용했다. 실제 메인 창이나 DB를 미리보기로 생성하지 않는다.
- `main.py`: 읽기 전용 건강 검사 뒤 `fresh`일 때만 설정창을 열고, 취소하면 DB 초기화·메인/트레이 생성 전에 정상 종료한다. 확정 뒤 데이터를 다시 확인하고 초기 크기를 신규 DB 생성에 전달한다. 기존 사용자와 HWP worker의 실행 경로는 유지한다.
