# 작업 기록: 화면 글자 따기 정확도 진단 도구 개발 계획

작성일: 2026-10-10 / 상태: 1~3단계 및 4단계용 등록·검토 창 구현, 실제 자료 확대·브라우저 시각 확인·단계별 진단 남음

현재 구현·검증과 미확인 항목은 [첫 구현 기록](2026-10-10-screen-text-lab-implementation.md), 실제 명령과 현재 범위는 [사용법](../SCREEN_TEXT_LAB.md)을 따른다. 아래 내용은 전체 1~6단계 계획이며 후속 자료 확대와 단계별 진단을 포함한다.

실제 PNG의 여러 개 등록·원본 확대·정답/표/조건 편집·검토 상태·새 자료 버전 저장은 [등록·검토 후속 기록](2026-10-10-screen-text-lab-review.md)에 구현·검증했다. 실제 캡처 500개나 최종 평가 자료를 이미 확보했다는 의미는 아니다.

후속 [조건 진단 기록](2026-10-10-screen-text-lab-conditions.md)에서 합성 원문 200종×12조건 2,400개로 확대하고 dev 1,920개를 실제 제품 엔진으로 측정했다. holdout 480개는 인식하지 않았다. 원본 1,000개 확보와 실제 환경/단계별 후보 실험은 남아 있다.

## 목표와 범위

- 목표: 다양한 화면에서 OCR 오류를 재현하고, 캡처·검출·인식·줄/표 구성·불확실 표시 중 어느 단계에서 발생하는지 조사한다. 변경 전후의 개선과 신규 오류를 실제 이미지로 비교한다.
- 이번 변경 대상: 이 계획, [검증 지침](../TESTING.md), [화면 글자 따기 계약](../SCREEN_TEXT.md)의 개발용 진단 안내. 제품 코드와 진단 도구 구현은 이번 작업에 포함하지 않는다.
- 구현 위치: `tools/screen_text_lab/`. 시험 자료는 `output/screen_text_lab/corpus/`, 실행 결과는 `output/harness/<run-id>/`에 둔다.
- 데이터 영향: 실사용 AppData·DB·salt·기존 실행 중인 앱을 읽거나 수정하지 않는다. 개발용으로 생성하거나 명시적으로 등록한 시험 이미지와 정답만 저장한다.
- 유지할 계약: 제품 오프라인 동작, 캡처 메모리 전용, 모델 MANIFEST 검증, 텔레메트리 끔, 차단 시 우회 금지, 자동 단어 교정 금지, DB v17·Export v2·설정 키·바로가기 6슬롯·모델/사전·Qt/lock 유지.
- 제외 범위: 상시 화면 수집, 제품 내 진단 메뉴, 클라우드 OCR, 자동 모델 다운로드/학습, 제품 기본값 자동 적용, EXE 빌드·배포·커밋·push.
- 시작 시 사용자 변경: `AGENTS.md`, `docs/RELEASE_HISTORY.md` 수정과 기존 미추적 작업 기록을 보존한다. 기존 디자인 점검·OCR 예비 실험 산출물도 유지한다.

## 결정과 진행

- 2026-10-10: 사용자는 특정 단어 교정보다 전체 정확도 개선을 요청하고, 다양한 상황을 실험하는 큰 진단 장치 개발 계획을 요청했다.
- 원본 100개는 도구 검증용 시작 규모다. 본격 평가 목표는 서로 다른 원본 약 1,000개, 조건별 시험 5,000~10,000건이다. 이 숫자를 통계적으로 충분한 표본 수나 실제 확보량으로 표현하지 않는다.
- 대규모 진단은 별도 명령으로만 실행한다. 코딩·앱 시작·통상 pytest·`quick/data/full/release`·일반 빌드·Git 훅/CI에서 자동으로 실행하거나 예약하지 않는다.
- 정답 검증·채점·비교·보고서 직렬화 같은 가벼운 자체 검사는 기존 `tests/`에 둔다. 이 신규 자체 검사는 실제 OCR 세션, 큰 자료 묶음, 실제 화면 캡처를 실행하지 않는다. 기존 `test_screen_text_engine.py` 등의 소규모 실제 모델 회귀는 그대로 유지한다.
- [예비 실험](2026-10-10-screen-text-accuracy-pilot.md)에서는 측정기의 줄 정렬 오류를 발견해 집계를 폐기했고, 수정한 실험에서도 개선 후보마다 신규 오류가 있었다. 기존 144조건은 개발용 시작 자료이며 최종 평가 자료로 재사용하지 않는다.
- 기존 `tools/verify.py`의 실행 ID·원자적 보고서 저장·격리 경로 규칙을 재사용한다. 하네스 프로필·빌드 호출 그래프는 확장하지 않는다. 세부 처리 계측 때문에 제품 변경이 필요하면 독립 변경으로 기록하고 결과 불변을 검증한다.

## 파일과 실행 경계

아래는 구현 예정 위치다. 이 계획을 저장한 시점에는 도구와 시험 자료를 생성하지 않는다.

```text
tools/screen_text_lab/
  __init__.py             import 시 실행·자료 탐색·모델 로드 없음
  __main__.py             명시적인 CLI 진입점
  corpus.py               정답·출처·조건·분할 검증
  generate.py             합성 자료와 조건별 변형 생성
  runner.py               격리 작업·진행 기록·중단·시간 제한
  engine_adapter.py       실제 제품 경로와 단계별 진단 연결
  metrics.py              채점과 원본 단위 집계
  compare.py              동일 자료의 두 실행 비교
  report.py               오프라인 HTML 생성
  recipes/                공개 가능한 합성 문구·조건 JSON
tests/
  test_screen_text_lab.py 가벼운 자체 검사, 필요할 때 역할별 분리
  fixtures/screen_text_lab/ 작은 합성 정답/결과 예제만 저장
output/screen_text_lab/corpus/
  <dataset-version>/     manifest·원본 이미지·정답·변형 이력
output/harness/<run-id>/
  result.json            실행 상태·환경·집계·자료/코드 해시
  cases.jsonl            사례별 결과·오류·시간
  summary.md             결과 요약과 미확인 범위
  report.html            요약·검색·조건별 필터·실행 비교
  cases/                 사례별 HTML·원본/영역 이미지
  logs/                  실행기 진단 로그
  appdata/               실행별 격리 경로
```

모듈은 필요한 단계에서 순서대로 추가한다. 범용 플러그인 시스템이나 별도 서버는 만들지 않는다. 제품에서 `tools.screen_text_lab`을 import하지 않으며 `build.spec`의 datas/hiddenimports에도 추가하지 않는다. 결과와 대량 자료는 기존 `output/` ignore 규칙을 따른다. 소량의 공개 가능한 합성 재료와 자체 검사 예제만 Git으로 관리한다.

`screen_text/`가 제거된 환경에서도 도구의 도움말·자료 검증·기존 보고서 비교와 가벼운 자체 검사는 동작해야 한다. 실제 인식 명령은 선택형 앱 부재를 명확한 환경 오류로 종료한다. 제거 절차에 진단 도구를 함께 제거하는 선택 사항을 추가한다.

### 명령 설계

아래 명령은 구현 후 제공할 인터페이스이며 현재 실행 가능한 명령이 아니다. 프로젝트 루트 PowerShell과 기존 Python 3.13 가상환경을 사용한다.

```powershell
.\.venv\Scripts\python.exe -m tools.screen_text_lab generate --profile bootstrap --seed 20261010
.\.venv\Scripts\python.exe -m tools.screen_text_lab validate --corpus output/screen_text_lab/corpus/v1
.\.venv\Scripts\python.exe -m tools.screen_text_lab run --corpus output/screen_text_lab/corpus/v1 --suite bootstrap --split dev --candidate baseline
.\.venv\Scripts\python.exe -m tools.screen_text_lab compare --baseline <기준실행ID> --candidate <후보실행ID>
```

- `bootstrap`: 개발용 원본에서 최대 100개를 고정 선택한다. 시험 자료가 부족하면 실제 수를 표시한다.
- `standard`: 선택한 분할의 원본 전체를 평가한다. 기본 분할은 개발용이며 최종 평가용은 `--split holdout`을 명시해야 한다.
- `stress`: 선택한 분할에서 미리 정의한 조건 조합을 실행한다. 무한 조합이나 자동 확대는 하지 않는다.
- 실행 전 대상 원본 수·파생 조건 수·모델/후보·분할을 표시하고 결과에도 기록한다. 예상 시간은 같은 PC에서 측정한 근거가 있을 때만 범위로 표시한다.
- 비교는 새 실행 폴더를 만들고 이전 산출물을 덮어쓰지 않는다. 중단한 실행은 `cancelled` 또는 `incomplete`로 남긴다. 자동 재시도는 하지 않는다.

## 시험 자료 구성

### 규모와 분리

1. 첫 100개로 정답 검토와 진단 도구의 채점·시각화를 검증한다.
2. 원본 약 1,000개까지 늘린다. 초기 수집 목표는 합성 원본 약 500개와 시험용 내용을 실제 프로그램에 표시해 캡처한 원본 약 500개다. 실제 확보량을 출처별로 표시하며 한쪽 부족을 다른 쪽 자료로 채워 완료 처리하지 않는다.
3. 원본 단위로 약 80% 개발용, 약 20% 최종 평가용으로 고정한다. 목표 규모 기준 약 800/200개이며 같은 문서·내용에서 나온 화면은 `source_group_id`로 묶어 한쪽에만 배정한다.
4. 배율·명암·여백 등의 변형은 부모의 분할을 상속한다. 같은 문장이나 화면의 변형을 독립 원본으로 세지 않는다. 동일 해시와 내용/출처 중복을 검토한다.
5. 개발용 자료에 조건별 5,000~10,000건을 구성한다. 최종 평가용의 원본·변형은 별도로 집계하며 후보 조정에 사용하지 않는다. 최종 결과를 보고 조정했다면 다음 최종 평가에는 새로운 보류 자료를 확보한다.

전체 수만으로 대표성을 판단하지 않는다. 프로그램·내용·글자 크기·명암별 사례 수와 오류를 표시하고, 부족한 조건을 우선 추가한다. 실제 오류 사례는 지속적으로 개발용 회귀 자료에 추가하되 기존 결과와 정답 버전을 보존한다.

### 내용과 환경

| 축 | 포함할 조건 |
|---|---|
| 내용 | 한글 본문·받침·고유명사·기관/주소·한영 혼합·명령어/경로·기호·날짜/금액/단위 |
| 구조 | 한 줄·긴 줄·여러 문단·다단·표·테두리 없는 표·빈 셀·셀 안 여러 줄 |
| 글자 | 실제 사용 글꼴, 글자 크기·굵기·자간·줄 간격, 작은 글씨와 밀집 문서 |
| 화면 | 밝음/어두움·낮은 대비·색 있는 글자·선택 강조·글자 없는 영역 |
| 영역 | 글자 밀착·여백·가장자리·긴 세로 영역·넓은 영역·1920/2560/3840px급 입력 |
| 실제 환경 | Windows 배율 100/125/150/200%, 프로그램 확대율, 실제 픽셀 크기, 혼합 DPI |
| 품질 | 원본·축소·압축·흐림. 기울어진 스캔 등 알려진 지원 한계는 별도 스트레스 분류 |
| 실행 | 첫 로드·반복 실행·스레드 설정·인식 배치의 개수/폭·같은 입력의 반복성 |

합성 자료, 실제 프로그램 캡처, 사용자가 등록한 사례를 별도 집계한다. Qt로 만든 터미널 모양 이미지를 실제 Windows Terminal 캡처라고 부르지 않는다. 이미지 확대와 실제 DPI 변경도 구분한다. 설치되지 않은 한글/Excel이나 확보하지 못한 모니터 환경은 미실행으로 남긴다.

처음에는 한 조건씩 바꾸고, 오류가 집중된 조건의 조합을 추가한다. 시험용 프로그램에는 합성 내용을 표시한다. 기존 사용자 창을 자동 탐색·캡처하지 않고 화면 배율이나 시스템 설정도 무인으로 변경하지 않는다.

### 자료 형식과 정답 검토

manifest와 사례 JSON에는 `schema_version`, `case_id`, `source_group_id`, `parent_id`, `split`, `source_kind`, 이미지 상대 경로·SHA-256·물리 크기, 원문 정답, 조건 태그, 생성 seed/변형 규칙을 둔다. 실제 캡처에는 프로그램·버전·OS·글꼴·배율·캡처 방식을 기록하며 모르는 값은 추측하지 않는다.

줄 좌표·읽기 순서와 표 행/열·셀 정답은 해당 평가에 필요한 사례부터 주석을 달고, 주석 수준과 검토 상태를 기록한다. 좌표는 원본 이미지 기준으로 고정한다. 텍스트 정답만 있는 자료에 검출/표 구조 점수를 만들어 넣지 않는다. OCR 출력은 초안으로만 사용할 수 있고 검토된 정답만 점수에 포함한다. 검토되지 않은 자료는 미채점 수로 표시한다.

경로 이탈·없는 파일·잘못된 크기/좌표·중복 ID·해시 불일치·분할 누출·필수 정답 누락은 실행 전에 거부한다. 정답 수정은 새 자료 버전으로 기록하며 서로 다른 정답 버전의 점수를 직접 비교하지 않는다. 대량 자료는 Git에 없으므로 manifest·이미지·정답을 함께 보존하고 해시로 검증하는 재현용 묶음을 관리한다.

## 측정과 원인 진단

### 제품 기준 결과

기준 실행은 실제 `OcrEngine.recognize()`와 `build_blocks()`·`to_plain()`·`to_tsv()`·`to_html()`·불확실 표시 계산을 사용한다. 측정기 안에 제품의 인식·정렬 로직을 복사하지 않는다. 결과 문자열·상자 좌표·점수·줄/표 구조·경고 범위를 보존한다.

단계별 진단은 별도의 관측 실행으로 구분한다. 필요하면 진단 전용 어댑터가 실제 `_detect()`/`_read()` 호출을 감싸 중간 결과를 수집하되, 관측 유무에 따른 결과가 같은지 검증한다. 실제 모델을 사용하는 이 대조는 명시적인 진단 명령에서 수행한다. 계측 시간을 기본 처리 시간과 섞지 않는다.

| 진단 | 입력과 비교 | 알아낼 내용 |
|---|---|---|
| 전체 처리 | 원본 이미지 → 실제 제품 최종 결과 | 사용자가 받는 결과의 정확도 |
| 위치 찾기 | 정답 줄 영역 ↔ 검출 영역 | 누락·중복·과도한 합침/쪼갬 |
| 글자 인식 | 정답 영역으로 자른 이미지 → 실제 인식 경로 | 위치 오류 영향을 줄인 인식 성능 |
| 줄과 표 | 정답 상자/글자 → 제품 layout | 읽기 순서·공백·행/열·셀 배치 오류 |
| 경고 | 정답과 대조한 오류 ↔ 제품 불확실 표시 | 틀렸는데 경고 없음·맞았는데 경고 |
| 캡처 | 시험용 실제 창 → 제품 캡처/선택 경로 | 물리 픽셀·영역 좌표·DPI·경계 잘림 |

고정 이미지 재생만으로 실제 캡처 경로를 검증했다고 표시하지 않는다. 정답 crop 실험도 실제 사용자의 전체 처리 정확도로 집계하지 않는다. 현재 디코더의 상자 평균 점수는 그대로 기록하고, 문자별 점수 등 추가 관측은 실제 수집 가능한 단계에서만 제공한다.

### 채점 규칙

- 주 지표는 공백 포함 글자 오류율 `CER = (치환 + 누락 + 삽입) / 정답 글자 수`와 원본/줄 완전 일치율이다. CER은 1을 넘을 수 있으며 임의로 자르지 않는다. 정답이 빈 화면은 CER 분모에서 제외하고 잘못 검출한 글자 수·빈 화면 성공률을 따로 센다.
- 채점용 문자열은 Unicode NFC와 줄바꿈 LF만 통일한다. 공백·대소문자·기호·닮은 글자를 자동 수정하지 않는다. 원문은 그대로 남기고 공백 제외 점수는 보조 지표로 병기한다. 한글 음절을 기본 글자 단위로 사용한다.
- 숫자·금액·날짜·단위는 주석된 항목의 완전 일치를 별도 계산한다. 표는 셀 내용과 행/열 위치를 함께 평가하며 빈 셀을 포함한다. 읽기 순서를 무시한 점수로 전체 정확도를 대체하지 않는다.
- 검출은 주석 단위를 줄 영역으로 맞추고 원본 좌표의 IoU 0.5 이상에서 일대일 매칭한 정밀도/재현율을 기본으로 한다. 임계값과 매칭 규칙을 버전 관리하고 합침/쪼갬 사례를 별도로 표시한다. 주석이 없는 사례는 해당 지표의 분모에 넣지 않는다.
- 경고는 오류가 있는 사례 중 무경고인 비율, 경고가 오류 위치를 포함하는 비율, 정답 영역의 과잉 경고를 함께 본다. 누락되어 상자 자체가 없는 글자도 오류로 센다. 모델 점수를 정답 확률로 표기하지 않는다.
- 전체 글자 수 가중 점수와 원본별 평균, 출처/조건별 점수를 함께 표시한다. 변형이 많은 원본 하나가 전체 결과를 지배하지 않도록 원본 수와 파생 조건 수를 분리한다.
- 실패·시간 초과·중단·미지원·미채점을 누락하지 않는다. 정확도와 별도로 처리 성공률 및 분모를 표시하고 성공한 사례만으로 전체 성능을 주장하지 않는다.
- 속도는 모델 첫 로드, 반복 처리 전체 시간, 단계별 계측 시간을 구분한다. 같은 PC·동일 설정에서 정한 반복 횟수와 워밍업 규칙을 기록하며 중앙값·95백분위·최대 메모리를 표시한다. HTML/파일 저장 시간도 별도 기록한다.

실행 결과에는 코드/미추적 코드·모델/사전·자료·설정 해시, Git 커밋과 변경 상태, seed, OS/CPU/메모리·Python/라이브러리·스레드·실행 명령을 남긴다. 시작과 끝의 입력 해시가 다르면 `inputs_changed`로 비교를 무효화한다. 중간 결과를 사례별로 남겨 중단해도 완료 분량과 실패 위치를 확인할 수 있게 한다.

## HTML 보고서와 비교

첫 화면에는 자료 버전·분할·원본/파생 수·처리 성공률·주 지표·경고·속도와 조건별 약점을 표시한다. 사례를 열면 원본 이미지, 확대 보기, 검출 상자, 정답과 실제 문자열의 차이, 표의 행/열, 경고 위치, 조건과 시간을 함께 보여 준다. 파생 이미지는 원본과 구별하고 실제 캡처의 픽셀을 보존한다.

비교 화면은 같은 `case_id`와 입력/정답 해시를 가진 결과를 짝지어 개선·신규 오류·유지로 분류한다. 부분 교집합 비교를 명시적으로 요청한 경우에만 허용하고 빠진 사례 수를 표시한다. 프로그램·내용·배율·명암·오류 단계·무경고 오류 필터와 문자열 검색을 제공한다. 신뢰 구간을 계산할 때는 파생 이미지가 아닌 원본/문서 묶음을 재표집 단위로 삼는다.

수천 장의 원본을 한 HTML에 모두 넣지 않는다. `report.html`에는 경량 집계를 내장하고 사례별 HTML/이미지에 상대 링크를 둔다. 더블클릭으로 열 수 있도록 CDN·외부 폰트·네트워크·로컬 서버·`fetch()`에 의존하지 않는다. OCR 문자열과 파일명은 HTML/스크립트에 안전하게 이스케이프하며 명령어나 링크로 실행하지 않는다.

## 구현 순서와 단계별 완료 조건

| 단계 | 구현 범위 | 완료 조건 |
|---|---|---|
| 1. 자료와 채점 | 자료 스키마·검증·고정 분할·텍스트/표 채점·CLI 골격·작은 자체 검사 | 손으로 계산한 치환/누락/삽입·공백·빈 정답·한글·표 위치 예제가 일치하고 잘못된 자료를 거부한다. import/도움말/자체 검사에서 OCR 세션과 대량 자료를 읽지 않는다 |
| 2. 기준 실행 | 실제 제품 어댑터·격리 worker·모델 검증·실행 ID·중단/시간 제한·결과 저장 | 명시적으로 선택한 소수 실제 모델 사례가 제품 결과와 일치한다. 실패/중단/입력 변경을 통과로 쓰지 않고 실사용 데이터에 접근하지 않는다 |
| 3. 보고서와 비교 | 원본/문자 차이·상자·표·필터·두 실행 비교 | 의도적으로 만든 개선/신규 오류/무경고 오류를 실제 이미지에서 찾을 수 있다. 네트워크 없이 보고서를 열며 100개 자료에서 사용성을 확인한다 |
| 4. 자료 확대 | 약 1,000개 원본·출처/조건 할당·정답 검토·5,000~10,000조건 생성 | 자료별 검토 상태와 약 800/200 분할이 확인된다. 실제 캡처·합성·파생의 수와 미확보 조건이 구분되며 고정 manifest로 재실행할 수 있다 |
| 5. 단계별 실험 | 정답 crop·검출/배치/레이아웃 관측·후보 설정 비교·실제 캡처 경로 시험 | 같은 입력에서 단계별 오류를 조사하고 계측 유무의 결과 불변을 확인한다. 최소 한 후보를 기준과 비교하고 개선·유지·신규 오류 여부를 보고서에서 확인한다. 실제 환경 결과는 고정 이미지 결과와 분리한다 |
| 6. 최종 평가 절차 | 후보를 고정한 뒤 보류 자료 평가·취약 조건 재검토·실행 안내 | 조정에 쓰지 않은 자료에서 결과와 처리 비용을 확인한다. 제품 적용 여부의 근거를 남기고 수동 미확인 환경을 구분한다. 도구의 정확한 사용/제거 절차를 정본에 반영한다 |

첫 구현 묶음은 단계 1~3이다. 이 묶음이 완료된 뒤 자료와 진단 범위를 확대한다. 후보 실험은 한 번에 한 요인을 바꾸는 것부터 시작하고, 검출 해상도/경계·배치/전처리·모델·줄/표·경고 순서를 오류 분포에 따라 조정한다. 도구 완성을 특정 후보의 정확도 향상과 혼동하지 않는다.

제품 적용은 별도 변경으로 진행한다. 비교 전 주 지표·필수 조건별 허용 퇴행·처리 시간/메모리 한도를 기록하고, 기준은 초기 측정과 사용 환경을 바탕으로 정한다. 평균 점수만으로 적용하지 않으며 새로 틀린 사례와 숫자/표·무경고 오류를 검토한다. 모델 변경이 필요하면 기존 무결성·라이선스·의존성·빌드 계약을 따른다.

## 검증 계획

- 작은 자체 검사는 고정된 합성 문자열/상자·임시 자료·가짜 엔진을 사용한다. 채점 오류, 분할 누출, 입력 변경, 중단, 비교 누락, HTML 이스케이프처럼 결과 신뢰성에 영향을 주는 동작을 검사한다.
- 실제 OCR 자료 생성·모델 비교·대량 평가 함수는 pytest 수집 시 실행하지 않는다. 명시적인 CLI가 실행하기 전에는 `corpus/`를 탐색하지 않는다. import나 자체 검사에서 실제 세션 생성/화면 캡처가 일어나면 실패하는 가드를 둔다.
- 자체 검사 개발은 `quick --tests tests/test_screen_text_lab.py` 등 관련 경로로 검증한다. 공용 실행기·격리 계약을 변경하면 `full`을 실행하며 같은 변경에서 하위 검사를 의무적으로 중복 실행하지 않는다.
- 단계 2~3의 실제 모델 기준 대조와 100개 예비 진단, 단계 4~6의 대량/실제 환경 진단은 별도 명령과 실행 ID로 남긴다. 기존 `quick/data/full/release`, `build_app.py`, `build.bat`에는 대량 진단을 연결하지 않는다.
- 최종 도구 검증에서 보고서의 실제 이미지·필터·확대·실행 비교·좁은 창 표시를 브라우저로 확인한다. 측정기 통과가 실제 혼합 DPI나 제품 EXE 검증을 대신하지 않는다.
- 개발 도구만 변경했다면 EXE를 새로 만들지 않는다. 제품 또는 패키징 변경이 생긴 경우 해당 변경에 맞는 하네스를 실행하고, 실제 빌드에서는 TOC로 도구/시험 자료 미포함을 확인한다.
- 현재처럼 문서만 변경한 작업은 링크·합의된 정책·현재 코드와의 사실 일치·기존 지침 보존을 검사한다. 과거 OCR 결과를 현재 계획의 구현 완료 근거로 사용하지 않는다.
