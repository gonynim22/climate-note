# 작업 기록: 화면 글자 따기 그림자 동그라미(❍)

작성일: 2026-11-10 / 상태: 구현·검증 끝, 커밋 전(v4.9 개발 범위 안)

## 목표와 범위

- 목표: 화면에 있는 그림자 동그라미 `❍`(U+274D)를 원문대로 낸다. 인식 모델의 사전에 없어 모델이 내지 못하고, 줄 맨 앞 기호 규칙이 고리로 보아 크기에 따라 `○`·`ㅇ`로 냈다. 지금 제품(`b5dot`)의 25개 평가 자료 17,082장에서 정답 `❍` 1,007곳 중 맞은 곳은 0이었다(함평군 업무계획 PDF 875곳, 고산·군산 조건 자료 22, 엣지·한글·엑셀 화면 21곳 등).
- 변경 대상: `screen_text/leading_symbols.py`(고리 판정에 그림자 비), `screen_text/engine.py`(조각 상자 거르기의 예외 기호에 `❍`), 시험 2개 파일, `docs/SCREEN_TEXT.md`·`AGENTS.md`·`docs/RELEASE_HISTORY.md`.
- 데이터 영향: 없다. DB·설정·암호화·Export 형식을 건드리지 않는다. 화면 글자 따기 판독 글자만 바뀐다.
- 제외 범위: 큰 동그라미 `◯`(크기가 `○`와 겹쳐 가를 수 없다), 그림자 네모 `❏`(합성 기호 자료에만 있다), 표 칸 표시 규칙(`cell_marks`), 모델 교체·언어 모델 교정.
- 시작 시 사용자 변경: `docs/SCREEN_TEXT.md` 5~6행의 사용자 두 줄(커밋 때 뺀다). 사용자 결정(2026-11-10): v4.9는 릴리스 확정이 아니라 개발 범위라 이 작업도 v4.9 안에서 한다.

- [x] 구현할 동작과 유지할 계약: 줄 맨 앞 고리 중 오른쪽 그림자가 진하고 네 꼭짓점이 빈 것만 `❍`로 낸다. `○ ㅇ ◯`와 그림자 네모는 지금처럼 고리로 내어 확인 필요로 둔다. 판독 글자를 추정하지 않고 화면 모양만 읽는다.
- [x] 관련 자동 검사: 새 시험 8개(실제 화면 회색 값 3종·크기 2종·기호만 든 상자·조각 거르기)가 고치기 전에 6개 실패, 고친 뒤 통과. 일부러 넣은 실수 네 가지(둘레 1px 빼기·꼭짓점 조건 빼기·`❍` 확인 필요 표시·문턱 1.2)를 모두 시험이 잡았다. 글자 따기 quick `20261110-182754-9e00923ef4` 1,676개 통과.

## 결정과 진행

- 2026-11-10: 남은 개선 거리를 25종 결과로 쟀다(`analysis-20261106/scripts/err_all.py`·`ctx_pairs.py`·`ring_where.py`). `❍→○` 1,007곳이 가장 큰 깨끗한 덩어리였다(줄 맨 앞 `◆` 223줄, 남는 `|` 약 320곳, 목차 점선은 한 쪽이 조건 11개로 반복된 것). 사용자가 "따 정확도"로 `❍`를 골랐다.
- `❍` 983곳이 줄 맨 앞이고 그중 928곳은 이미 고리로 잡혀 `○`(781)·`ㅇ`(147)로 나왔다. 엣지·엑셀의 '줄 안' `❍`도 표 칸의 첫머리라 같은 규칙이 맡는다. 그래서 고칠 곳은 `leading_symbols._classify`의 고리 갈래 하나다.
- 특징(`ring_log.py`로 고리로 판정된 4,161개 덩어리의 회색 진하기와 정답 기호를 짝지음, `ring_feats.py`·`ring_margin.py`): 가운데 행 띠(높이 0.3~0.7)의 오른쪽 절반 진하기 합 / 왼쪽 절반 합. 200% 함평군 문서의 `❍`는 왼쪽 획 2px·오른쪽 4~5px, 100%·80%도 1px 대 2px로 그림자가 남는다.
  - 덩어리 상자 안만 재면 GDI로 그린 대칭 `○`가 1.7~2.06까지 나왔다. 왼쪽 획이 두 열로 옅게 나뉘어 바깥 열(56/255)이 글자 픽셀 문턱(가장 진한 값의 0.3배, 76)에 못 미쳐 상자에서 잘렸기 때문이다. 둘레 1px까지 재면(오른쪽은 뒤 글자와의 틈 안에서만) 정답 `○` 391개 ≤1.29, `ㅇ` 1,781개 ≤1.14, `◯` 55개 ≤1.23, `❍` 677개 ≥2.0으로 갈린다. 문턱은 그 사이 1.6이다.
  - 위아래 비는 `❍`도 1 안팎이라(0.88~1.14) 쓰지 않았다. 대신 네 꼭짓점 칸(폭·높이의 10%)이 모두 비어야 한다. 고리로 잡힌 진짜 `❍` 929개가 모두 비었고, 비율만으로 걸린 가짜 13개 중 11개(그림자 네모 `❏`, 고리로 오인된 `p`·작은 조각)는 꼭짓점이 찼다.
  - `❍`는 확인 필요로 표시하지 않는다. 고리를 표시하는 까닭은 `ㅇ ◦ ○ o`를 모양으로 가를 수 없어서인데, 그림자는 모양으로 분명하다(■ □ ◇ -와 같은 취급). 지금 `❍` 자리마다 붙던 노란 표시가 없어진다.
- 시안(`snap/ring0`=제품 복사, `ring1` 비율만, `ring2` +꼭짓점, `ring3` +조각 예외. 패치 `scripts/ring_patches/patch_shadow.py`·`patch_keep.py`): `ring1`은 나아짐 355·나빠짐 0·같음 13(가짜 `❍` 13), `ring2`는 같음 2로 줄었다. `ring2`에서 함평군 한 줄의 기호가 사라진 것을 보고 원인을 찾았다: 엔진의 조각 상자 거르기(`_fragment_boxes`)는 점수 0.7 미만의 한두 글자 상자를 큰 글자 옆이면 버리는데, 예외 기호 `FRAGMENT_KEEP`에 `○`는 있고 `❍`는 없어 기호만 든 `❍` 상자(점수 0.47)가 버려졌다. `ring3`에서 `❍`를 더해 2장이 더 나아졌다.
- 놓친 13곳(함평군): 기호만 든 상자의 오른쪽 끝이 그림자를 1~2px 잘라 비율이 0.7~1.5로 떨어진다. 상자 밖까지 보려면 기호 탐색 범위를 바꿔야 하고 다른 기호에 영향이 가서 이번에는 두었다.
- 제품 = `snap/ring3`(평가한 코드와 상수 주석 한 줄만 다르다).

이 파일은 진행 기록이다. 영구 지침은 [화면 글자 따기 계약](../SCREEN_TEXT.md)과 `AGENTS.md`에 반영한다.
