## 결정과 진행

- 2026-11-09 기준 측정(`scripts/speed_stages.py`, 두 번 평균, 모델 스레드 4). cProfile은 Python 3.13에서 인식 모델 실행 구간을 놓쳐(21회 중 3회만 잡힘) 단계별 실제 시간으로 쟀다.

  | 입력 | 전체 | 모델(위치+인식) | 모델 밖 | 큰 항목 |
  |---|---|---|---|---|
  | A4 한 쪽 `page-100` | 2.83초 | 1.60초 | 1.23초 | 위치 찾기 입력 크기 바꾸기 0.37, 표 선 찾기 0.20, 2배 0.09, 인식 상자 크기 바꾸기 0.10, 기호 규칙 약 0.25 |
  | 빽빽한 쪽 `dense-100` | 3.79초 | 2.02초 | 1.77초 | 크기 바꾸기 0.58, 표 선 0.29, 글머리 0.12, 기호 규칙 약 0.35 |
  | FHD `fhd-1p075` | 4.68초 | 2.38초 | 2.30초 | 위치 찾기 입력 크기 바꾸기 1.02(띠 3개 각 0.3), 2배 0.20, 표 선 0.16 |
  | 4K `uhd-2p150` | 6.41초 | 3.34초 | 3.07초 | 표 선 찾기 0.99, 여백 두르기 0.26, 크기 바꾸기 0.38, 글머리 0.14, 기울기 0.10 |

- v4.0과 견주면 느려진 까닭의 대부분은 정확도를 올린 단계 자체다(2배로 다시 찾기, 넓은 영역을 원래 크기로 띠 나눠 찾기, 상자 수 증가). 모델 실행은 판독을 바꾸지 않고는 줄일 수 없으므로 모델 밖 시간만 줄인다.
- 모델 스레드 수는 바꾸지 않는다: 4→6이면 A4 한 쪽 판독 해시가 달라졌다(점수 비트가 바뀐다). 업무 PC마다 코어 수가 다르면 점수 비트도 그 PC에서 정해지는 셈이라, 이 작업은 같은 스레드 수에서 전과 같은 값을 낸다. 인식 세션의 실행마다 메모리 돌려주기는 시간에 영향이 없었다(21회 1.02~1.05초, 그대로 둔다).
- 1단계(모델 밖 계산): 크기 바꾸기는 가로 보간을 원본 줄마다 한 번만 하고 큰 이미지는 스레드로 나눈다(가로 보간은 float64에서 정확해 나눠 계산해도 같다), 정수 배 평균은 정수 합(합이 2^24 아래라 float32 합과 같고 나누기는 np.mean과 같은 ufunc 호출), 2배는 줄 묶음·스레드, 여백 두르기는 맨 윗줄에서 끝까지 이어진 열이 없으면 전체를 재지 않는다, 위치 찾기 입력은 실수 사본 없이 채널 평면에 바로 채운다(바탕색은 크기를 바꾼 그림의 둘레만 따로 계산), 표 선 찾기는 np.median 대신 같은 값을 내는 partition 계산·행 구간을 한꺼번에·상자 반복을 배열로·능선과 계단을 256줄씩, 상자 하나의 규칙들이 같은 crop의 글자 픽셀 기준을 한 번만 잰다(`shared_ink`, 잰 crop을 블록 끝까지 쥐어 메모리 주소가 다른 배열에 다시 쓰이지 않는다), 글머리 기호의 상자×상자 반복을 배열로, 덩어리 모양 특징은 필요할 때만.
- 2단계(겹치기): 인식 모델은 전용 스레드에서 묶음 순서대로 돌고 그동안 앞 묶음의 글자 규칙과 다음 묶음 입력을 만든다(인식 모델이 쉬는 시간 A4 0.002초), 표 선 후보(`grid_lines`)는 다음 위치 찾기 모델이 도는 동안, 기울기용 글자 픽셀과 표 선용 회색 그림은 첫 위치 찾기 모델이 도는 동안 다른 스레드에서 만든다.
- 메모리를 보고 뺀 것(제품 사본을 하나씩 끈 변형 `snap/fast2_*`, `scripts/speed_mem_variants.py`): 다음 띠 입력을 앞 띠의 모델이 도는 동안 만들기는 FHD·QHD 0.12초 빨랐지만 최대 메모리 +23~37MB(입력 하나), 4K는 빨라지지 않았다. 2배 이미지를 첫 위치 찾기 동안 미리 만들기는 빨라지지 않았고 150% 쪽에서 +27MB. 표 선 찾기의 회색 변환이 그림 크기의 float32 사본(4K 99MB)을 잠깐 만들어 큰 입력의 위치 찾기와 겹치면 최대가 그만큼 올랐으므로 회색 그림은 첫 위치 찾기 동안 만든다(같은 행렬곱이라 값은 같다). 남은 증가는 표 선 후보를 큰 입력과 함께 재는 몫이다(4K +40~50MB, 대신 0.37초 빠르다).

## 미해결과 인계

- 남은 문제 / 수동 확인: 업무 PC 시간(코어가 4개보다 적으면 겹치기 이득이 줄어든다). 큰 영역의 첫 최대 메모리 증가(4K +40~50MB)는 표 선 후보 겹치기의 대가다. 두 번 인식한 프로세스 전체의 최대(OS 최대 작업 집합)로 보면 24개 중 19개가 같거나 줄었고, 가장 큰 값은 603→554MB로 내려갔다. 5MB 넘게 는 것은 4K 화면 둘뿐이다(`uhd-3p` 481→526, `uhd-5p100` 480→520). 그래서 이 증가는 그대로 둔다(2026-11-09 사용자 결정). 더 줄일 수 있는 직렬 조각은 각각 1% 안팎이다(4K 표 선 찾기의 상자 판정 0.06초, 여백 두르기 0.04초, 띠 사이 라벨링 0.01초씩, 글머리 기호 0.05초).
- 변경한 정본 문서: `docs/SCREEN_TEXT.md`(속도 항목, 큰 영역 시간), `AGENTS.md`(글자 따기 계약의 속도 문장), `docs/RELEASE_HISTORY.md`(v4.8 배포 뒤 수정).
- 다음 행동: EXE·버전·`release`는 다음 글자 따기 작업과 묶어 만든다(2026-11-09 사용자 동의). 남은 글자 따기 과제는 남은 낫표·『』, 1,936px 넘는 영역 2배.
- 교훈(2026-11-09 밤): 이 작업은 판독을 비트 단위로 비교했지만 EXE를 빌드하지 않아, 새로 쓴 표준 라이브러리 `concurrent.futures`가 `build.spec`에서 빠진 것을 놓쳤다. 이 커밋으로 만든 EXE는 없다(첫 release가 잡았다). 엔진 import를 바꾼 작업은 `release`까지 돌린다(`AGENTS.md` 명령 절).
- 배포·커밋·push 여부: 이 기록이 든 커밋을 GitLab → GitHub `main`에 push했다(2026-11-09). EXE·버전·`release`는 하지 않았다.
