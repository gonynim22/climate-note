## 결정과 진행

- 2026-10-10: 사용자는 원본이 Windows CLI 화면이었다고 설명했다. 이번 예비 실험은 사용자 원본의 재현을 주장하지 않는다. 화면 글자 따기 계약의 오프라인·자동 글자 교정 금지·메모리 전용 런타임을 유지한다. 실험 파일은 개발용 합성 자료만 보존한다.
- 기준 문서: [화면 글자 따기 계약](../SCREEN_TEXT.md), [검증](../TESTING.md). 수정 범위를 좁히는 karpathy-guidelines 스킬을 적용한다.
- 첫 보조 실행은 cp949 로그 인코딩 오류로 중단했다. r2는 문자 상자를 y좌표로만 합쳐 실제 앱 줄 구성과 달라지는 측정 오류가 있어 집계값을 폐기했다. r3는 제품 `build_blocks()`/`to_plain()`/`unsure_count()`를 그대로 사용해 새 실행에서 재측정했다.
- r3 터미널 유사 합성 96조건: 공백 무시 완전 일치 현재 77, 밝은 극성 후보 81(개선 5·신규 오류 1), 여백 2px 확대 76(개선 5·신규 오류 6). 이 수치는 전체 앱 정확도가 아니며 ‘커밋 → 커및’은 미재현이다. 잘못된 결과를 경고하지 않는 사례는 재현했다.
- 사용자 추가 지시: ‘커밋 → 커및’에 국한하지 않고 전체 정확도를 개선한다. 본문·기관/주소·받침·한영·CLI·수치·날짜·표 12종 × 3글자 크기 × 2명암 × 2선택 폭으로 144조건 비교를 시작했다.
- 공식 PaddleX 인식 전처리는 최소 320px 패딩과 전체 CTC 출력 디코딩을 사용한다. 현 구현의 최소 폭 미설정·폭 비례 출력 절삭과의 차이를 후보로 비교하되, 공식 형태라는 이유만으로 교체하지 않는다. 출처: https://raw.githubusercontent.com/PaddlePaddle/PaddleX/develop/paddlex/inference/models/text_recognition/processors.py
- 전반 144조건에서 현재 처리의 공백 무시 완전 일치는 108개/글자 편집 거리 합 46(정답 5520자)이었다. 최소320 패딩은 109개/45, 상자별 단독 인식은 112개/45, 밝은 극성+320 패딩은 112개/37이었다. 각 후보에서 기존 정답 손상 1/2/4건이 있어 공통 기본값을 변경하지 않았다. 전체 정확도 수치로 일반화하지 않는다.
- 다음 개발 순서: (1) 일반 화면 평가 범위와 미사용 확인 집합 확보, (2) 검출·경계·중복/누락 개선, (3) 인식 전처리 및 한국어 모델 비교, (4) 띄어쓰기/표 재구성 개선, (5) 경고 판정의 별도 개선. 자동 단어 치환은 추가하지 않는다.
