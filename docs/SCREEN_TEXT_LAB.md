# 화면 글자 따기 정확도 진단 도구

개발자가 시험 이미지와 정답을 등록해 실제 제품 OCR 결과를 측정하고, 원본 이미지·인식 상자·문자 차이를 오프라인 HTML로 확인하는 도구다. 인식 로직을 바꾸기 전후에 같은 자료를 실행하고 개선과 신규 오류를 비교한다.

도구는 `tools/screen_text_lab/`에 있다. **대규모 진단은 아래 명령을 명시적으로 실행할 때만 동작한다.** 앱 시작·일반 빌드·통상 pytest·`quick/data/full/release`·훅/CI에 연결하지 않는다. `tests/test_screen_text_lab.py`에는 모델 없이 작동하는 작은 자체 검사만 있으며 기존 제품의 소규모 OCR 회귀 검사는 유지한다.

학습 환경을 준비하는 `training.bootstrap`의 다운로드는 고정된 CPython 버전과 PaddleOCR 리비전의 공식 HTTPS 주소 두 개만 허용한다. HTTPS 전용 처리기와 기본 인증서 검증을 사용하고 HTTPS 프록시는 유지하며, 파일/HTTP/FTP 주소·임의 주소·리디렉션을 거부한다. 기존 파일을 덮어쓰지 않는다. 이 수동 개발 도구는 EXE에 포함하지 않으며 실제 학습은 보류 상태다.

## 첫 사용

프로젝트 루트 PowerShell에서 기존 Python 3.13 가상환경을 사용한다. 패키지를 자동 설치하거나 lock을 갱신하지 않는다.

```powershell
.\.venv\Scripts\python.exe -m tools.screen_text_lab --help
.\.venv\Scripts\python.exe -m tools.screen_text_lab generate --profile bootstrap --seed 20261010
```

두 번째 명령은 직접 만든 한글·CLI·한영·숫자·날짜·문서·기호·표 100개를 Qt로 그린다. 모든 자료는 개발용 합성 이미지이며 실제 프로그램 캡처가 아니다. 숫자를 바꾼 표는 같은 원본 그룹으로 묶는다. 기존 자료를 덮어쓰지 않고 `output/screen_text_lab/corpus/<새 ID>/`를 출력한다. 생성 seed와 문구/글꼴·배경·크기 조건을 manifest에 기록한다. 같은 seed라도 시스템 글꼴/Qt 환경이 다르면 픽셀이 달라질 수 있으므로 이미지 해시와 실제 글꼴을 확인한다.

출력된 경로를 아래 `<자료 폴더>` 자리에 넣는다.

```powershell
.\.venv\Scripts\python.exe -m tools.screen_text_lab validate --corpus "<자료 폴더>"
.\.venv\Scripts\python.exe -m tools.screen_text_lab run --corpus "<자료 폴더>" --suite bootstrap --split dev --candidate baseline
```

`bootstrap`은 지정 분할의 원본 중 최대 100개, `standard`는 그 분할의 모든 사례를 처리한다. 보류 자료는 `--split holdout`을 명시해야 한다. 스레드 수는 `--threads 1` 같은 형태로 지정하고 모델 로드/각 사례 시간 제한은 `--timeout 120`으로 지정한다. 기본 후보는 실제 제품 `baseline`이다. 실험 후보는 아래 고정 목록에서 명시적으로 선택하며 제품 기본값을 바꾸지 않는다.

완료 후 출력된 `output/harness/<실행 ID>/report.html`을 브라우저로 연다. 결과 폴더 전체를 보존해야 사례별 HTML과 PNG 링크가 유지된다. 외부 서버·CDN·폰트·네트워크 요청은 사용하지 않는다.

## 같은 원문의 화면 조건 진단

`conditions` 프로필은 직접 작성한 문장/CLI/문서/숫자/기호/화면 안내 180종과 서로 다른 표 20종에 동일한 12조건을 적용한다. **원문 200종, 이미지 2,400개**이며 변형을 원본으로 더 세지 않는다. 기존 bootstrap에서 사용한 원문 80종은 개발용으로 유지한다. 새 원문 중 40종(480개 이미지)은 최종 평가용 `holdout`으로 분리하고, 조건을 탐색할 때는 개발용 160종(1,920개 이미지)만 실행한다.

```powershell
.\.venv\Scripts\python.exe -m tools.screen_text_lab generate --profile conditions --seed 20261010
.\.venv\Scripts\python.exe -m tools.screen_text_lab validate --corpus "<새 자료 폴더>"
.\.venv\Scripts\python.exe -m tools.screen_text_lab run --corpus "<새 자료 폴더>" --suite standard --split dev --candidate baseline
```

조건은 기준(16px 밝은 배경), 10/12/24px, 어두운 배경, 낮은 대비, 넓은 선택 영역(최소 1600px), 2px 여백, 조밀한 줄, Batang 명조체, 합성 125/150%다. 같은 원문을 다시 그린 이미지마다 부모·그룹·분할·동일 정답을 기록한다. 글자 크기·여백·줄 간격을 함께 키운 합성 배율은 실제 Windows DPI/ClearType 재현을 뜻하지 않는다. `font_resolved`는 기본 글꼴 family이며 한글/기호별 대체 글꼴은 따로 측정하지 않는다. 표의 빈 셀은 표 정답에 보존하며 문자 탭 정답에서는 비어 있는 셀을 건너뛴다.

보고서의 **같은 원문, 화면 조건만 바꾸면** 표는 조건별로 기준과 둘 다 채점된 원문 쌍만 집계한다. CER와 기준 대비 %p, 공백 제외 CER, 문자열 일치, 무경고 오류, 개선/악화 수와 악화 예시 원본 링크를 제공한다. 누락·실패·미채점은 비교 대상에서 사라지지 않고 `result.json`의 `condition_analysis`에 수를 남긴다. 내용 종류별 쌍 결과도 같은 JSON에 포함한다. 전체 CER은 시험 조건을 같은 비중으로 섞은 수치이며 실제 업무 비중을 반영한 정확도가 아니다. 최종 평가 자료는 모델/설정 후보를 정하기 전에는 인식하지 않는다.

생성 순서는 seed로 고정하며 이전 자료를 덮어쓰지 않는다. PNG와 manifest를 함께 보존해야 재현할 수 있다. 이 중간 확대는 원본 약 1,000개/실제 프로그램 캡처 확보의 완료를 뜻하지 않는다. [조건 진단 기록](work/2026-10-10-screen-text-lab-conditions.md)을 따른다.

## 변경 전후 비교

동일 자료로 변경 전과 변경 후 각각 `run`을 실행한 뒤 실행 ID를 지정한다. 도구가 제품의 인식/줄·표 구성 함수를 직접 호출하므로 제품 소스 변경을 기준으로 비교할 수 있다.

```powershell
.\.venv\Scripts\python.exe -m tools.screen_text_lab compare --baseline <기준실행ID> --candidate <후보실행ID>
```

사례 ID·원본 이미지·정답·분할·원본 그룹·조건·검토 상태가 같고 채점 규칙 버전이 같은 결과만 짝지어 비교한다. 부분 교집합을 의도한 경우에만 `--intersection`을 지정하며 제외된 자료 수를 표시한다. 저장된 결과 JSONL과 원본 이미지의 해시도 확인한다. 입력 변경/중단된 실행을 완료된 결과처럼 비교하지 않는다. 두 실행의 산출물은 그대로 두고 새 비교 폴더를 만든다.

보고서는 편집 오류 감소를 개선, 증가를 퇴행으로 분류한다. 편집 오류가 같으면 표 셀 오류로 비교하고, 그 값도 같으면 원문 변화 여부를 구분한다. 경고 수와 시간은 별도로 검토해야 한다. 평균 점수 상승만으로 제품 변경을 채택하지 않는다.

### 전처리 후보와 문자 점수 관측

`--candidate`는 다음 고정 목록만 받는다. 임의 코드나 외부 모델을 불러오지 않는다. 모든 후보는 개발용 실험이며 제품 기본값이 아니다.

| 후보 | 기준과 달라지는 값 |
|---|---|
| `baseline` | 없음: 현재 제품 경로 |
| `upscale-2` | 전체 입력을 최대 2배로 확대. 기존 긴 변 4000px 상한 유지 |
| `det-1600` | 위치 검출 입력의 긴 변 상한 960→1600px |
| `unclip-1.2` | 검출 상자 확장 비율 1.5→1.2 |
| `det-aspect` | 검출 입력의 가로세로 비율 유지, 끝 픽셀로 32배수 크기 패딩 |
| `rec-320` | 인식 입력 최소 폭 320px, 전체 CTC 출력 디코딩 |
| `rec-light` | rec-320 + 균일한 어두운 배경의 인식 영역 반전 |
| `rec-ink` | rec-light + 실제 픽셀 경계와 글자 높이 20% 여백으로 인식 영역 정규화 |
| `rec-ink-native` | 픽셀 정규화하되 기존 배치 폭·CTC 절삭 유지. 높이 4px 미만/입력 폭 2배 초과 변환은 제외 |
| `det-ink-native` | det-aspect + rec-ink-native |
| `rec-selective` | 기존 점수 <0.97 영역만 한 번 추가 인식. 비어 있지 않고 점수가 0.02 이상 오른 결과만 선택 |
| `rec-selective-stable` | rec-selective + 공백 제외 글자가 같으면 원래 문자열·점수 유지 |
| `rec-short-6` / `rec-short-10` | 균일 배경의 긴 줄을 픽셀 높이 6/10배 목표로 빈 열에서 분할해 재인식. 같은 비공백 글자/빈 구간은 원래 결과 유지 |

예: 같은 자료에 `run --corpus "<자료 폴더>" --suite standard --split dev --candidate det-1600`을 실행하고 baseline 실행과 `compare`한다. baseline은 제품 경로를 그대로 사용한다. 후보는 소유 worker 안에서 한 호출 동안 상수 또는 검출/인식 메서드를 바꾸고 성공·실패·취소 때 원복한다. 제품 디코더·줄/표 구성·채점은 공통이다. 목록에 고정한 조합만 제공하며 자동 최적화는 하지 않는다. 추론에 정답·영역 주석·자료 태그를 사용하지 않는다.

**2026-11-06부터 `baseline`(제품 경로)에는 공백 복원이 들어 있다**([계약](SCREEN_TEXT.md)). 그 이전 실행 결과와 직접 비교하면 공백 오류가 줄어든 것처럼 보인다. `preprocessing.py`·`recognizers.py`처럼 `_read` 반복을 따로 복제한 후보(`rec-*`·`--recognizer`·`--input-profile`)는 공백 복원을 쓰지 않으므로, 이 후보들과 baseline을 비교할 때는 공백 포함 지표 대신 공백 제외 지표를 본다. 글머리 기호 복원(`leading_symbols.py`, 2026-11-06)은 `recognize()`가 `_read` 뒤에 한 번 적용하므로 후보를 포함한 모든 제품 경로에 같이 들어간다. 그 이전 실행과 비교하면 줄 첫머리 기호(`■ □ ◇ ㅇ`)가 늘어난 것으로 보이며, 진단 결과의 `boxes`에는 `unsure_prefix`가 추가되었다. 낫표 복원(`corner_brackets.py`, 2026-11-06)은 공백 복원과 같이 `_read` 안에서 적용되므로 `_read` 반복을 복제한 후보에는 들어가지 않는다. 이 후보들과 baseline을 비교할 때는 `[ ]`와 `「 」`의 차이를 후보 효과로 읽지 않는다.

`prediction.trace`에 검출/인식 시간, 처리 이미지 크기, 검출 상자 수, 디코딩 영역 수, 출력된 비공백 문자 수와 그 최소 CTC 점수를 남긴다. 원래 디코더가 출력한 문자와 관측 대상 문자가 같음을 확인하며 인식 텍스트·상자 점수·제품 경고를 수정하지 않는다. 문자 점수는 정답 확률이 아니며 빠진 문자는 점수가 없어 관측에서 놓칠 수 있다.

재인식으로 상자 수보다 많이 디코딩한 사례는 `score_scope=all_hypotheses`다. 이때 문자 수/최소 점수에는 거절된 대안도 포함되므로 최종 출력만의 문자 통계가 아니며 최소 점수 기반 모의 경고 표에서는 제외한다. 실제 제품 경고 수와 무경고 오류 채점은 별도로 유지한다.

보고서의 모의 경고 표는 제품 경고에 문자 최소 점수 `<0.5/0.7/0.8/0.9`를 각각 추가한 사례 단위 결과다. 잡은 오류뿐 아니라 놓친 오류·정상 결과 오경고·정상 무경고를 모두 표시한다. 공백·표 포함 기준과 공백 제외 글자 기준을 나란히 보고, 관측이 없거나 미채점/실패인 사례를 분모에서 구분한다. 위치별 경고 적중률을 뜻하지 않는다.

후보 비교의 `candidate_analysis`와 HTML 표에는 동일하게 채점된 쌍만 사용한 공백 포함/제외 CER, 기존 정답 손상/오류 복구, 표 셀 정확도, 1회 시간 비율과 내용/화면 조건별 결과를 남긴다. 예전 실행에 관측이 없으면 모의 경고를 소급해서 만들지 않는다. 후보/판단 기준을 먼저 고정하고 dev에서 탐색하며 holdout은 후보 선정 뒤 별도 평가한다. [후보 실험 기록](work/2026-10-10-screen-text-lab-candidates.md)을 따른다.

짧은 구간 후보는 `trace.short_regions`에 원래 줄·점수·분할 좌표·구간별 실제 판독·사용/보존 이유를 남긴다. 픽셀 밝기 차이로 빈 열을 추정하며 정답/사전/태그를 자르는 위치에 쓰지 않는다. 배경이 복잡하거나 안전한 틈이 없으면 원문을 유지하고 최대 16구간으로 제한한다. 글자가 달라진 결합 결과의 점수는 글자 수 가중 평균으로 관측용이며 보정된 정답 확률이 아니다. 검출 상자와 줄/표 구성은 유지한다. 실제 메모장 dev 48개에서는 공백 제외 오류 129→129/130자, 기존 정답 손상 각 1개로 사전 기준에 미달했다. 이 두 후보의 탐색을 종료하고 제품 적용·합성 dev 확대·holdout 평가는 하지 않았다. 고정 계획·원본 위 분할 표시·실제 판독과 검증은 [짧은 구간 실험 기록](work/2026-10-11-screen-text-short-regions.md)을 따른다.

## 영역 검출과 글자 판독 분리

다음 명령은 평소 baseline 인식 뒤에 주석 좌표를 사용하는 추가 인식 2회를 실행한다. **`--diagnose-regions`를 명시했을 때만 실행**되며 첫 버전은 `--candidate baseline`에만 허용한다.

```powershell
.\.venv\Scripts\python.exe -m tools.screen_text_lab run --corpus "<자료 폴더>" --suite standard --split dev --candidate baseline --threads 4 --diagnose-regions
```

원본 `regions`의 `box`(원본 픽셀의 x0,y0,x1,y1 반열림 좌표)와 `text`를 사용한다. 영역은 읽기 순서로 나열하고, 공백 제외 원문 전체가 그 순서대로 일치해야 한다. 정답 문자열은 인식 뒤 채점에만 쓰며 제품 인식기 `_read`에는 이미지와 좌표만 전달한다. 주석 그대로(`as-annotated`)와 사방 2px 확장(`pad-2`, 이미지 경계에서 자름)을 고정 비교한다. 현재 합성 주석은 글꼴 치수 사각형이며 완벽한 글리프 경계가 아니므로, 이 결과를 인식 모델의 이론적 최고 정확도로 부르지 않는다.

`prediction.region_diagnostic`에 영역별 직접 인식 결과·엄격/공백 제외 오류, 제품 줄·표 구성을 거친 전체 결과, 주석 순서대로 이어 붙인 공백 제외 결과와 별도 추가 시간이 남는다. 제품 경고·텍스트·기존 `total_ms`는 바꾸지 않는다. 후자는 추가 진단 시간을 포함하지 않는다. 추가 진단 실패는 기존 제품 결과를 보존하고 실행 상태를 `partial`로 남긴다.

주석 없음, 영역별 정답 없음, 미검토, 불완전 주석/읽기 순서 불일치, 입력 축소·확대 발생, 상자 수 상한 초과는 각각 제외 상태로 남긴다. 첫 버전은 주석 최대 256개·검출 최대 512개, 제품의 `MAX_SIDE`를 넘지 않고 `UPSCALE=1`인 입력을 지원한다. `region_analysis`의 전체/관측/비교/제외 수와 상태별 수를 함께 확인한다. 제외 자료를 정상 정답으로 세지 않는다.

단계 표는 동일하게 비교 가능한 사례의 기존 제품 CER, 직접 인식+제품 구성 CER, 직접 인식+주석 순서 CER을 공백 제외 기준으로 표시한다. 회복/신규 오류/양쪽 오류는 기존 제품과 **주석 순서 결과**의 완전 일치 여부이며, 원인을 확정적으로 분류한 숫자가 아니다. 순서까지 알려주는 효과와 줄·표 구성의 영향을 구분해 읽는다. 표 구조 점수는 제품 layout을 거친 결과에만 부여한다. 영역별 오류 합계도 별도 저장해 서로 다른 영역에서 생긴 오류가 합친 문자열에서 상쇄되는 경우를 확인한다.

원본 그림의 파란 점선은 주석 영역, 기존 주황/붉은 테두리는 실제 텍스트를 출력한 제품 상자다. 빈 결과로 걸러진 상자까지 포함한 검출 원본은 `trace.detection_boxes`와 단계 기하 정보에 보존한다. 기하 관측은 합집합 피복률(겹친 면적 중복 합산 없음), 가장 많이 겹친 상자의 높이 비율, 분할/합침/중복 가능성이다. 교집합/작은 사각형 면적 ≥0.5를 대응/큰 겹침, 합집합/주석 면적 <0.5를 낮은 피복, 높이 ≤8px 또는 폭 ≤3px를 작은 검출로 센다. 이 기준은 확정 누락/중복 정답 판정이 아니다.

현재 실행과 수동 미확인 범위는 [영역 진단 기록](work/2026-10-10-screen-text-lab-regions.md)을 따른다. 실제 업무 캡처·최종 평가용 자료는 이 합성 dev 실험과 별도로 다룬다.

## 모델 출력·CTC 디코딩 진단

`--diagnose-ctc`는 baseline의 실제 인식 모델 출력과 제품 디코더 입력을 관측한다. **명시적인 수동 옵션**이며 `--diagnose-regions`와 동시에 사용할 수 없다. `--case-id`를 반복 지정하면 선택한 suite/split 안의 특정 사례만 실행한다. 중복·없는 ID는 실행 전에 거부한다.

```powershell
.\.venv\Scripts\python.exe -m tools.screen_text_lab run --corpus "<자료 폴더>" --suite standard --split dev --diagnose-ctc --case-id cond-cli-002--font10 --case-id cond-table-012
```

`prediction.ctc_diagnostic`와 사례 HTML에 다음을 남긴다.

- 실제 배치 순서·공유 메모리 대조, 독립적인 반복/blank 제거 결과와 제품 출력 일치 여부.
- 절삭 전/후 단계 수와 전체 출력 greedy 문자열, 단계별 상위 5개 문자·blank 점수·argmax 연속 구간.
- 같은 절삭 출력의 prefix beam(width 8, 상위 5개+blank+prefix 끝 문자). 사전·언어 모델·정답을 추론에 쓰지 않는 근사 탐색이며 최적 문자열을 보장하지 않는다.
- 추론 후 위치가 명확히 1:1 대응하는 영역의 정답/제품/beam 문자열 CTC 경로 log mass. 공백 포함과 공백 클래스를 blank에 합친 공백 제외 조건을 구분한다. 같은 영역·같은 조건끼리 비교하며 정답 확률로 해석하지 않는다.

제품 반환 텍스트·상자·점수·복사·경고는 유지한다. 가상 비교 `full_greedy`와 `beam8`은 기존 상자 점수를 그대로 사용하므로 후보 신뢰도/경고 정확도 평가가 아니다. **관측 중 `total_ms`·인식 시간에는 진단 계산이 포함되어 제품 지연시간 비교에 사용할 수 없다.** 모델 재추론은 없으며 전체 확률 행렬은 저장하지 않는다.

입력 축소와 검출 상자 128개 초과는 각각 `input_resized`/`box_limit`로 제외하고, 영역 출력 1,024단계 초과는 `step_limit`/사례 `limited`로 남긴다. 미검토·주석 없음·모호한 겹침은 정답 경로 점수에서 제외한다. 관측 실패는 제품 결과를 보존하고 진단 오류와 실행 `partial`을 남긴다. 모델 자체 실패와 구분한다. `ctc_analysis`의 대상/비교/상태별 수를 함께 확인한다.

2026-10-11 고정 선택표는 `tools/screen_text_lab/recipes/ctc-diagnosis.json`이다. 15원문·76개 합성 PNG(기존 dev 50개, **이미 사용한 holdout 26개**)를 원인 탐색에 사용했다. 232개 영역의 반복/blank 처리는 독립 계산과 같았고, 절삭 영역 85개를 모두 읽어도 문자열은 바뀌지 않았다. 공백 제외 오류 영역 47개 모두에서 현재 모델 분포는 정답보다 제품 오답의 경로 질량이 컸다. beam8은 160→155자 오류를 줄였지만 완전히 복구한 사례는 0개였다. 입력 전처리와 모델 자체를 단독으로 구분한 결과가 아니며 독립 정확도 개선 근거로 사용하지 않는다. 제품 적용은 없고 [진단 작업 기록](work/2026-10-11-screen-text-ctc-diagnosis.md)에 실행·검증을 남긴다.

## 입력 조건·인식 모델 비교

`--recognizer`를 명시하면 고정된 제품 검출 영역에서 인식 모델/입력 조건을 비교한다. `--candidate baseline`에서만 지원하며 영역·CTC 추가 진단과 동시에 사용하지 않는다. 일반 실행·제품·빌드는 이 비교 경로를 사용하지 않는다.

```powershell
.\.venv\Scripts\python.exe -m tools.screen_text_lab run --corpus "<자료 폴더>" --suite standard --split dev --recognizer product --input-profile native
.\.venv\Scripts\python.exe -m tools.screen_text_lab run --corpus "<자료 폴더>" --suite standard --split dev --recognizer product --input-profile ink-light
.\.venv\Scripts\python.exe -m tools.screen_text_lab run --corpus "<자료 폴더>" --suite standard --split dev --recognizer easyocr-korean-g2 --input-profile native
```

모델은 `product`(번들 한국어 v5), `paddle-korean-v3`, `easyocr-korean-g2` 중 하나다. 대체 모델은 `output/screen_text_lab/models/<모델 ID>/`에 개발용으로 따로 보관하며 `tools/screen_text_lab/recipes/recognizers.json`의 고정 공급자·리비전·크기·SHA-256을 확인한다. 인식 실행은 다운로드/패키지 설치/외부 코드 import를 하지 않고 누락·불일치를 거부한다. 모델과 사전 클래스 수·입력 shape도 세션 생성 후 확인한다. 번들 모델/사전/라이선스·의존성 lock과 EXE를 바꾸지 않는다.

개발자가 자산을 준비할 때 registry의 각 `files[].url`에서 내려받아 `name`으로 두고 크기·SHA-256을 대조한다. EasyOCR `dict.txt`는 고정된 `config.py`의 `recognition_models['gen2']['korean_g2']['characters']` 문자열 리터럴을 AST로 읽어 한 글자씩 LF 줄로 저장한 파생 파일이다. 원격 Python을 실행하지 않는다. 해당 원문도 `upstream-config.py.txt`로 보존하고 검증한다. 사전 첫 공백을 유지하고 blank/공백을 추가하지 않는다. Paddle v3는 공식 CTC 계약대로 공백을 추가하며, 원 사전의 공백과 더해 두 클래스가 같은 공백에 대응하는 상태를 유지한다.

| 입력 조건 | 변화 |
|---|---|
| `native` | 원 crop과 모델 고유 입력 규칙 유지 |
| `single` | 한 영역씩 인식해 배치 패딩 영향을 분리 |
| `pad-2` / `pad-4` | crop 사방에 끝 픽셀 2/4px 연장. 정규화 후 글자 크기·여백 변화 |
| `light` | 균일한 어두운 배경만 반전. 좌표/크기 유지 |
| `ink` | 균일 배경에서 픽셀 경계와 글자 높이 20% 여백으로 정규화. 밝기 유지 |
| `ink-light` | ink + 어두운 배경 반전 |

복잡한 배경·대비 부족·작은 획·정규화 폭 폭증에서는 원 crop을 유지한다. 정답·영역 주석·태그로 전처리나 모델을 선택하지 않는다. 검출 좌표·원 crop 해시·전처리 크기·정규화 tensor 해시·배치 폭·사용 출력 단계를 각 결과에 남긴다. 두 모델 비교 결과에 원 crop/검출 좌표가 다르면 비교를 거부한다.

Paddle 두 모델은 48px BGR/이중선형/0 패딩/비율 절삭, EasyOCR g2는 64px 회색조/Pillow bicubic/끝 픽셀 패딩/전체 CTC 출력을 사용한다. EasyOCR는 로컬 변환 인식 모델의 어댑터 비교이며 전체 EasyOCR 검출/대비 재시도/전용 신뢰도 파이프라인을 재현하지 않는다. 같은 원 crop을 사용해도 두 계열의 정규화 tensor는 다르다. 공통 greedy CTC와 기존 줄·표 구성을 유지하며, CTC 평균 점수·경고는 모델 간 보정하지 않았으므로 직접 신뢰도 비교에 쓰지 않는다.

실행 보고서에 인식 모델 용량, 사전 밖 정답 글자(추론과 분리한 평가용), worker 프로세스 전체 최대 working set을 남긴다. 모델 파일 크기는 EXE 크기와 다르고 메모리는 모델만의 사용량이 아니다. 시간은 입력 해시 관측 포함 1회 처리이며 반복 성능 측정이 아니다. 선택표 `recipes/model-input-comparison.json`과 [입력·모델 비교 기록](work/2026-10-11-screen-text-model-input-comparison.md)을 따른다. 이미 사용한 holdout을 다시 튜닝하거나 새 최종 평가로 부르지 않는다.

## 실제 CLI 캡처 수집 묶음

원본 PNG가 아직 없을 때 `capture-kit`으로 새 CLI 문구 30개(6분류×5개)와 수집 안내를 준비한다. 이 명령은 **문구만 생성하며 화면 캡처·OCR·환경 설정 변경을 하지 않는다**. 첫 수집 절차 확인용 규모이며 전체 업무 정확도의 대표성이나 기존 원본 1,000개 확보 목표의 완료를 뜻하지 않는다.

```powershell
.\.venv\Scripts\python.exe -m tools.screen_text_lab capture-kit
.\.venv\Scripts\python.exe -m tools.screen_text_lab show-capture --kit "<생성된 수집 폴더>"
.\.venv\Scripts\python.exe -m tools.screen_text_lab import-captures --kit "<수집 폴더>"
```

수집 묶음은 `output/screen_text_lab/capture/<ID>/`에 생성한다. `Start.cmd`를 사용자가 더블클릭하면 프로젝트 `.venv`로 표시 명령을 실행한다. 기존 Windows Terminal/PowerShell 환경에서 촬영하려면 위 `show-capture`를 그 터미널에서 직접 실행한다. 표시된 명령어 예문은 텍스트로만 출력하며 실행하지 않는다. Enter로 다음 문구, 1~30으로 이동, q로 종료한다. `--case-id cli-batchim-01`처럼 지정하면 해당 본문만 출력한다.

- 안내/입력 프롬프트를 제외한 본문 전체를 원본 PNG로 저장한다. `captures/cli-batchim-01.png`처럼 화면에 표시된 이름을 쓰고, 다른 조건의 같은 문구는 `cli-batchim-01--dark.png`처럼 접미사를 붙인다. 파일명 접미사에서 실제 배율/테마를 추정하지 않는다.
- `environment.json`의 `common`에 확인한 프로그램/버전·Windows 배율·앱 확대·글꼴/크기·테마를 적는다. 모르는 값은 빈 문자열로 유지하고, 환경이 다른 개별 PNG는 `per_file`에서 재정의한다. `plan.json`·원문·실행 파일 해시는 고정하며 변조/실수 변경 시 등록/표시를 거부한다.
- `import-captures`는 해당 `captures`의 PNG만 비재귀적으로 읽는다. 다른 폴더를 명시하려면 `--images "<PNG 폴더>"`를 쓴다. 계획에 없는 파일명·깨진 PNG·서로 다른 문구에 연결된 동일 PNG는 거부하며, 같은 문구의 동일 이미지 중복은 건너뛴다. 입력과 기존 corpus는 덮어쓰지 않고 새 검토용 사본만 생성한다.
- 새 자료는 `source_kind=user_supplied`, **정답 초안 미검토**로 등록한다. 화면 잘림·실제 줄바꿈·글리프 표시를 기존 `review` 창에서 원본과 대조한 뒤 확인 완료해야 채점된다. 실제 프로그램 캡처 여부/환경은 자동으로 인증하지 않는다. 시험 문구 기반 화면과 자연스러운 업무 화면 자료는 구분한다.
- 각 분류 01~04는 dev, 05는 holdout으로 PNG를 보기 전에 고정한다. 같은 문구의 모든 캡처는 같은 원본 그룹/분할이다. 보류 6개는 새 최종 평가 집합으로 확대할 자료이며 후보 확정 전 인식하지 않는다. 과거 평가 자료를 새 보류 자료로 바꾸지 않는다.
- 표시 원문은 문자 정답 초안이다. 열 모양 사례의 표 구조는 자동 정답으로 만들지 않고 검토 창에서 별도 입력한다. 촬영 자료가 일부뿐이어도 등록할 수 있으며 계획 30개와 실제 등록/검토 수를 구분한다.

출력된 corpus로 아래 검토 창을 열고 새 버전을 저장한 뒤 `run --suite standard --split dev`로 첫 기준을 측정한다. 자동 촬영·상시 수집·후보 선택·holdout 실행·통상 빌드/테스트 연결은 없다. 현재 확보량과 검증은 [실제 캡처 준비 기록](work/2026-10-11-screen-text-real-capture-intake.md)에 남긴다.

### Computer Use로 수집한 메모장 시험 자료

2026-10-11에는 별도 Computer Use 세션에서 새 메모장에 위 30개 시험 문구를 표시하고 실제 앱 확대 100/150%로 촬영했다. 진단 CLI에 자동 수집 명령을 추가한 것은 아니다. 원본 창 JPEG 12장과 사각형만 자른 PNG 60개를 보존하고 `program_capture`로 등록했다. 단일 앱·맑은 고딕 12pt·밝은 배경이며, 실제 CLI/Windows DPI/자연 업무 자료와 구분한다. 원본 JPEG 압축 영향과 역슬래시/원화 글리프 모호성도 기록했다.

AI의 원본 시각 대조 후 새 corpus를 저장하고 dev 48개만 측정했다. `baseline`과 `rec-selective-stable`의 공백 제외 CER은 모두 4.2914%(129 / 3,006자), 오답 22개 중 무경고 21개였다. 후보 제품 적용은 없으며 holdout 12개는 인식하지 않았다. 독립적인 사람의 정답 검토·전체 업무 정확도 검증으로 해석하지 않는다. 실행 ID·HTML·자료 경로와 제약은 [실제 메모장 수집 기록](work/2026-10-11-screen-text-computer-use-capture.md)을 따른다.

후속으로 동일 dev의 제품 native/ink-light/pad-2/pad-4와 로컬 대체 인식 모델 2개를 비교했다. 어느 후보도 전체 문자 오류를 줄이지 못했다. 원문을 유지한 native/ink-light 불일치 경고는 무경고 오류 화면을 21→4개로 줄였지만 정상 화면 26개 중 2개에도 경고했고, 실제 오류 위치를 가리킨 화면은 오류 22개 중 14개에 그쳤다. 같은 `갬→캠` 오답을 두 판독이 함께 내면 놓치며, 다른 정상 글자의 불일치 때문에 화면 경고만 생기는 경우도 있다. 판독 정확도·화면 경고·위치 적중을 별도로 보고 제품 적용은 보류했다. 원본 crop·6조건·분류별 결과·사전 기준과 검증은 [실제 자료 판독·경고 진단](work/2026-10-11-screen-text-real-capture-diagnosis.md)에 남긴다.

## 현재 한국어 소형 모델의 추가 학습 검토

후속 [업무 문서 OCR 강화 실행 계획](work/2026-10-11-screen-text-finetuning-plan.md)은 한컴 한글·PDF·Word·메모장의 본문/표/숫자·단위를 우선하며 총괄·학습·자료·평가 에이전트의 소유권과 단계별 판정을 정한다. 사전 유지 A와 업무 기호 확장 B를 분리하고, NRTR의 실제 길이 제한·warmup·문자 ID 재매핑·여러 자료 사이의 분할 누출을 검사한다. 사용자 승인 후 별도 환경의 실제 pilot 학습을 시작했으며 결과와 실패는 [실행 기록](work/2026-10-11-screen-text-finetuning-implementation.md)을 따른다. 제품 반영은 별도 평가 이후 단계다.

2026-10-11 [추가 학습 검토](work/2026-10-11-screen-text-finetuning-review.md)에서 공식 학습 가중치·설정·제품과 동일한 사전·Windows 학습/변환 도구 배포를 확인했다. 이 검토 시점에는 설치·재변환·학습·제품 교체를 하지 않았으며, 이후 실행 단계에서 공식 미학습 재수출과 현재 ONNX의 동일 입력 대조를 통과했다. 자료는 줄 crop/정답 쌍으로 만들고 길이 초과·사전 밖 글자 누락을 사전에 차단한다. 기존 실험 자료를 새 독립 평가로 재사용하지 않으며 실제 보류 12장은 후보 확정 전 열지 않는다. 학습 도구·가중치·환경은 개발 출력 폴더에만 두고 제품 모델/사전·lock·DB/설정·통상 테스트/빌드에 연결하지 않는다.

## PNG 등록·정답 검토 창

JSON을 직접 쓰지 않고 다음 명령으로 별도 개발용 창을 연다. 앱 시작·일반 빌드·통상 테스트에서는 이 창이나 대규모 평가가 실행되지 않는다.

```powershell
.\.venv\Scripts\python.exe -m tools.screen_text_lab review
.\.venv\Scripts\python.exe -m tools.screen_text_lab review --corpus "<이어서 검토할 자료 폴더>"
```

1. **PNG 추가**에서 시험용 캡처를 여러 개 선택한다. 같은 문서/화면의 변형은 같은 **원본 그룹**을 쓰고, 실제 캡처/합성/출처 미확인 및 개발용/최종 평가용을 지정한다. 선택한 파일만 읽으며 자동으로 화면을 찍거나 폴더를 수집하지 않는다. 동일 바이트 이미지의 중복 등록은 제외한다.
2. 원본을 **맞춤 / 100% / + / −**로 살펴보고 문자 정답을 입력한다. 공백·줄바꿈을 그대로 유지한다. 표는 **표 구조도 평가**를 켜고 Tab으로 셀, Enter로 행을 구분한다. 마지막 빈 셀은 Tab으로 남기며, 마지막 행 뒤에 불필요한 Enter를 넣지 않는다. 문자 정답과 표 정답은 별도로 입력한다.
3. 프로그램·내용 종류·테마·Windows 배율·앱 확대율·글꼴·글자 크기는 아는 값만 입력한다. 자동으로 추정하지 않는다. **원본을 대조해 정답 확인 완료**를 선택해야 채점된다. 문자/표를 수정하면 확인이 풀린다. 빈 정답을 확인 완료하려면 **글자 없는 화면으로 확인**도 선택한다.
4. **다음 검토 필요 사례**로 이동하면 입력은 현재 세션에 유지된다. 목록 검색/필터로 미검토 사례를 찾는다. **새 버전 저장** 또는 `Ctrl+S`로 `output/screen_text_lab/corpus/<새 ID>/`에 전체 PNG·정답 snapshot을 저장한다. 하단 상태 표시줄에 새 경로가 나온다. 첫 저장까지는 선택한 원본 PNG를 이동/수정하지 않는다.
5. 저장한 새 경로로 `validate`와 명시적 `run --suite standard`를 실행한다. 평가용 자료는 원본 그룹 단위로 개발용과 분리한다. 저장 시 동일 원본 그룹·이미지·내용의 분할 누출을 검사한다.

기존 자료 폴더·원본 이미지·이전 평가 결과는 덮어쓰지 않는다. 저장 실패 시 입력과 기존 버전을 유지한다. 창 닫기/다른 자료 열기는 미저장 입력의 저장·버리기·돌아가기를 제공한다. 검토 상태와 원본 이미지/정답을 저장할 뿐 OCR은 실행하지 않으며 인식 결과를 정답으로 자동 채택하지 않는다. 매 저장은 전체 사본이므로 큰 자료는 검토를 모아서 저장한다. 이전 버전은 자동 삭제하지 않는다.

기존 `regions` 등 추가 주석은 보존하며 이 창에서 상자 좌표를 편집하지 않는다. 기존 합성 `generated` 정답은 글자를 그대로 둔 조건 편집에서는 상태를 유지한다. 저장 구조는 아래와 같으며, [등록·검토 구현 기록](work/2026-10-10-screen-text-lab-review.md)에 검증 범위를 남긴다.

## 두 판독의 불일치 경고 진단

`disagreement`는 저장된 `product/native`와 `product/ink-light` 두 실행을 읽어, 원문을 유지하면서 다른 글자와 누락 가능 삽입점을 표시한다. 두 실행의 제품/입력 코드·모델/사전 해시가 같아야 하며 실행 중 입력 변경은 명령 실패로 처리한다. 모델 추론은 하지 않는다. 새 성능 측정은 별도 명령으로만 실행한다.

```powershell
.\.venv\Scripts\python.exe -m tools.screen_text_lab benchmark-disagreement --baseline <native 실행 ID> --candidate <ink-light 실행 ID> --repeats 5 --threads 4
.\.venv\Scripts\python.exe -m tools.screen_text_lab disagreement --baseline <native 실행 ID> --candidate <ink-light 실행 ID> --benchmark <성능 실행 ID>
```

- 공백 차이를 제외하고 최소 편집 거리를 사용한다. 동률 우선순위는 대각선→삭제→삽입으로 고정한다. 경고 생성 함수에는 두 출력 문자열만 전달하며 정답·태그·사전으로 글자를 고치지 않는다.
- 원문 기준 Python/UTF-16 위치를 함께 보존한다. 다른 글자는 강조하고 다른 판독에만 있는 글자는 길이 0 삽입점을 표시한다. HTML의 삽입점은 CSS 표식이라 원문에 문자를 끼워 넣지 않는다. 원본 PNG에서 개별 글자 픽셀 위치를 알아냈다는 뜻은 아니다.
- 화면 단위 TP/FN/FP/TN과 실제 표시 위치 적중을 나눈다. 정답에 대한 모든 최소 정렬에서 확실한/가능한 오류 위치를 계산한다. 범위는 정렬 모호성이고 통계 신뢰구간이 아니다. 반복 누락 문자는 한 삽입점으로 세므로 문자 오류 수와 다르다. 공백/표 구조 오류는 이 위치 평가 범위 밖이다. 미검토·미완료·NFC가 아닌 원문/정답은 위치 채점에서 제외하고 수를 남긴다.
- 성능 표본은 category×condition별 고정 seed 이미지 해시로 한 개씩 고르며 정답/예측/오류 수를 보지 않는다. 동일 모델 세션, 검출 1회, 추가 ink-light 인식 후 원문/표/복사/기존 경고를 유지한다. 워밍업 3쌍 후 순서를 교대해 반복 측정한다. PNG 읽기·캡처·세션 로드·UI는 제외하고 두 번째 판독/줄·표 구성/표시 계산은 포함한다. 결과는 이전 두 실행과 전 필드 해시로 대조한다.
- 실행은 소유 Windows Job·격리 AppData 안에서만 이루어진다. 취소/실패 시 임시 인식 함수 교체를 복원한다. 추가 판독 실패 때의 제품 UI 정책은 아직 구현하지 않았다. 파일/모델 다운로드, 제품 변경, 자동 빌드 연결은 없다.

보고서는 새 `output/harness/<run-id>/report.html`에 원본 합성 PNG, 원문 표시, 두 번째 판독, 정답과 위치 통계를 보존한다. 이미 사용한 개발 자료의 재분석이며 새 독립 정확도 검증은 아니다. 실제 증거는 [경고 진단 기록](work/2026-10-11-screen-text-disagreement-warning.md)에 남긴다.

## 불일치 경고 조건 비교

`warning-rules`는 완료된 불일치 분석을 입력으로 받아, 동일 모델과 저장된 검출 영역에서 native/ink-light 두 판독의 문자 점수를 추가 관측한다. 모든 텍스트·표·복사·상자/점수·기존 경고가 이전 결과와 동일한지 대조한 뒤 고정 조건을 비교한다. 정답/태그는 worker 요청에 넣지 않는다.

```powershell
.\.venv\Scripts\python.exe -m tools.screen_text_lab warning-rules --analysis <불일치 분석 실행 ID> --threads 4
```

규칙·선택 기준은 `tools/screen_text_lab/recipes/warning-rules.json`에 고정한다. 문자 점수 임계값, 두 판독의 점수 차이, 두 조건의 조합, 불일치 수, 누락 표시 조건 19개다. 반복/blank 처리 뒤 실제 출력한 시점의 CTC 최대값이며 정답 확률이 아니다. 삽입/누락 때문에 한쪽에 대응 글자가 없으면 인접 문자 최솟값을 쓰고 이를 증거에 표시한다. 값이 없으면 점수 기반 규칙으로 기존 불일치 경고를 지우지 않는다. 모든 조건은 원래 제품 경고를 유지한다.

분류별 원문 그룹을 고정 seed 해시로 정렬해 75% 조정/25% 확인으로 나눈다. 같은 원문의 모든 파생 조건은 같은 분할이다. 기존에 본 dev 자료를 재분할한 것이므로 새 독립 평가라고 해석하지 않는다. worker 실행 전에 `plan.json`에 recipe/그룹 배정을 저장하고, 조정 결과만으로 `selection.json`을 쓴 뒤 확인 정답의 위치를 채점한다. 확인 결과를 보고 다시 선택하지 않는다.

조정용 채택 기준은 오류 화면 경고와 확실한 오류 위치 적중을 각각 95% 이상 유지, 정상 오경고를 20% 이상 줄이고 CLI 확실 적중을 90% 이상 유지하는 것이다. 충족한 규칙 중 오경고 최소→확실 적중 최대→표시 수 최소→ID 순서로 고른다. 없으면 `all`을 유지한다. 확인용에서도 같은 기준을 확인하고, 통과 여부와 관계없이 실제로 놓친 오류·오경고·위치 적중을 함께 남긴다. 전체 결과는 설명용 재집계다.

출력은 새 하네스 폴더의 `features.jsonl`(문자 점수·영역 입력 해시·그대로의 두 판독), `details.json`(사례별 남긴 표시/채점), `result.json`, `summary.md`, `report.html`이다. 원본 PNG와 경고 감소/실제 오류 표시 손실 예시를 함께 보여 준다. 관측 시간에는 점수·해시 수집이 포함되므로 제품 지연시간으로 사용하지 않는다. 수동 명령에만 연결하며 모델 다운로드·제품 수정·빌드 자동 실행은 없다. [조건 비교 기록](work/2026-10-11-screen-text-warning-rules.md)을 따른다.

## 자료 등록 형식

등록·검토 창이 PNG와 `manifest.json`을 만든다. 수동으로 같은 형식의 자료를 작성해도 된다. 아래는 한 사례의 최소 형태이며 `image_sha256`에는 실제 파일의 SHA-256을 넣는다. 진단 도구 자체의 자동 화면 수집 명령은 제공하지 않는다.

```json
{
  "schema_version": 1,
  "dataset_id": "my-corpus-v1",
  "cases": [{
    "case_id": "terminal-001",
    "source_group_id": "terminal-document-001",
    "parent_id": null,
    "split": "dev",
    "source_kind": "program_capture",
    "review_status": "reviewed",
    "image": "images/terminal-001.png",
    "image_sha256": "실제 PNG 해시",
    "image_size": [800, 240],
    "expected": {"text": "정확히 확인한 원문"},
    "tags": {"category": "cli", "theme": "dark", "font_px": 16}
  }]
}
```

- `source_kind`: `synthetic`, `program_capture`, `user_supplied` 중 하나다. 실제 프로그램명/버전·Windows 배율·확대율·글꼴은 확인한 값을 `tags` 또는 `provenance`에 기록한다.
- `review_status`: 실제 자료는 정답 검토 후 `reviewed`, 미검토는 `unreviewed`다. `generated`는 합성 자료의 생성 문구를 정답으로 쓴 경우만 허용한다. 미검토 자료는 인식하되 채점하지 않는다.
- 표 정답은 `expected.table`에 동일한 열 수의 문자열 배열을 추가한다. 빈 셀도 `""`로 둔다. `expected.text`는 글자 탭에서 기대하는 읽기 순서와 줄바꿈/공백을 그대로 기록한다.
- 선택적인 `regions`는 `{"box": [x0, y0, x1, y1], "text": "..."}` 목록이다. 원본 픽셀 좌표로 범위를 검증하며 첫 버전에서는 검출 IoU 점수를 계산하지 않는다.
- 파생 이미지는 같은 문서/원본의 `source_group_id`와 분할을 유지하고 `parent_id`에 원본 사례 ID를 지정한다. 동일 내용·이미지가 개발용과 보류 자료 사이에 섞이면 거부한다.
- 이미지 경로는 자료 폴더 안의 상대 경로로 제한한다. ID 중복, 해시/크기 오류, 잘못된 정답·좌표·분할을 실행 전에 거부한다. PNG는 3,200만 픽셀 이하, 정답 텍스트는 8,192자 이하로 제한한다. 편집 거리 계산 조합이 400만 칸을 넘으면 해당 사례를 채점 오류로 남기므로 긴 문서는 영역별로 나눠 등록한다.
- 정답을 수정하면 새 자료 버전을 만든다. 대량 자료와 실행 폴더는 `output/`의 Git 제외 대상이다. 다른 PC에서 재현하려면 원본·정답·manifest를 함께 보존해야 한다.

## 점수 해석

기본 글자 오류율은 NFC/개행 LF만 통일한 문자열의 `(치환 + 누락 + 삽입) / 정답 글자 수`다. 공백을 포함하고, 공백 제외 결과도 사례별 JSON에 남긴다. CER은 100%를 넘을 수 있다. 정답이 빈 화면은 CER 분모에서 제외하고 잘못 나온 글자 수를 따로 집계한다.

문자열 완전 일치와 표의 내용/행/열 일치를 구분한다. 글자가 맞아도 표 구조가 틀리면 사례는 오류로 표시한다. 틀렸는데 제품의 확인 필요 표시가 0곳인 사례를 무경고 오류로 센다. 상자 평균 점수를 정답 확률로 표현하지 않는다. 현재 보고서의 주황 상자는 인식 영역, 붉은 상자는 평균 점수가 0.8 미만인 영역이며 테두리 색이 정답 여부를 뜻하지 않는다.

전체 글자 수 가중 CER과 원본 그룹별 평균, 출처·내용·글꼴·명암 등의 조건별 결과를 함께 남긴다. 사례별 실패·미실행·미채점을 숨기지 않는다. 현재 시간은 모델 로드 시간과 각 자료의 1회 처리 시간이며 워밍업·반복 실행 성능, 최고 메모리, 실제 캡처 지연은 측정하지 않는다.

## 실행과 데이터 보존

실행마다 고유 하네스 폴더와 격리 AppData를 만들고 Windows Job에 소유한 worker를 넣는다. 중단/시간 초과 때 그 Job만 정리한다. 진행 상태는 append JSONL로 전달해 Windows의 읽기/파일 교체 충돌을 피한다. 끝나지 않은 사례를 `not_run` 등으로 기록하고 완료 분량을 보존하며 자동 재시도하지 않는다.

`result.json`에는 설정·환경·자료·소스/모델 해시, `cases.jsonl`에는 정답과 사례별 결과, `cases/`에는 원본 PNG 사본과 HTML을 보존한다. 변경 검사는 실제 사용한 엔진/layout·모델·경로 처리·공유 실행 도구·진단 코드/재료/자체 검사·의존성 기록에 적용하며 무관한 UI 파일은 제외한다. 이 입력이 실행 중 바뀌면 `inputs_changed`, 보고서 생성이 실패하면 `report_error`로 남긴다. 정상적인 OCR 오탈자가 있어도 측정 자체가 완료되면 `completed`다. 이 상태는 인식이 모두 정확하거나 배포 검증을 통과했다는 뜻이 아니다.

실사용 DB/salt·기존 앱·제품의 캡처 메모리에는 접근하지 않는다. 제품의 메모리 전용·오프라인·자동 글자 교정 금지 계약은 [화면 글자 따기](SCREEN_TEXT.md)대로 유지한다. 진단 도구와 시험 자료는 EXE에 포함하지 않는다.

`screen_text/`를 제거하면 실제 `run`은 모델 환경 오류가 되지만 도움말·자료 등록/검토·자료 검증·기존 실행 비교는 사용할 수 있다. 진단 도구까지 없애려면 `tools/screen_text_lab/`, `tests/test_screen_text_lab*.py`와 이 문서의 관련 안내를 제거한다. 기존 시험 자료/실행 결과는 자동 삭제하지 않는다.

## 현재 범위와 후속 작업

현재 구현은 [개발 계획](work/2026-10-10-screen-text-lab-plan.md)의 자료 등록/검증·채점·실행·비교, 합성 원문 200종×12조건과 조건 쌍 분석, 고정 전처리 후보·검출/인식 시간·문자 점수 관측, 주석 영역 직접 인식 2조건과 기하 관측이다.

2026-10-11에는 개발용 1,920개로 후보를 고정한 뒤, 보류했던 40원문×12조건=480개에서 최초 엔진과 `rec-selective-stable`을 처음 평가했다. 공백 제외 오류 291→284(-2.4%)였지만 완전 일치 333→332, 표 셀 오류 42→43, 중앙 시간 1.33배로 채택 기준에 미달해 **제품 적용을 보류했다**. [개선·최종 평가 기록](work/2026-10-10-screen-text-accuracy-improvement.md)과 그 HTML에 원본·개선·퇴행 사례를 보존한다. 실제 제품 인식 엔진/모델/EXE는 바꾸지 않았다.

해당 480개는 이제 사용한 평가 자료다. 회귀 비교에 재사용할 수 있지만 이후 튜닝의 독립 최종 평가로 다시 주장하지 않는다. 다음 확증 평가는 새 원문 그룹과 실제 자료를 확보한다. 자료 약 1,000개와 5,000~10,000조건 확대·혼합 DPI·자연 업무 화면은 후속 범위다. 현재 합성 시험은 전체 업무 정확도를 대표하지 않는다.

2026-10-11 실제 메모장 시험 문구 캡처는 원문 30개×앱 확대율 2개로 확보했으며 dev 48장/보류 12장으로 구분했다. 단일 글꼴·밝은 테마·JPEG 유래·AI 정답 검토 자료이고 실제 CLI나 독립 사람 평가는 아니다. [짧은 구간 분할](work/2026-10-11-screen-text-short-regions.md)은 개선 기준에 미달해 탐색을 종료했다.

이어 [새 모델 두 후보 비교](work/2026-10-11-screen-text-new-models.md)에서 같은 dev 48장의 전체 텍스트 영역을 PaddleOCR-VL 1.6 / GLM-OCR Q8로 로컬 판독했다. Paddle은 공백 제외 문자 오류 129→70(-45.7%)였지만 기존 정답 화면 2장을 새로 틀렸다. GLM은 HTML 표의 태그를 제외한 사후 보조 집계에서도 306개 오류로 기준보다 나빴다. 두 후보 모두 고정 채택 기준 미달로 확대를 종료했고 보류 12장·제품 모델/코드/EXE는 유지했다. 새 모델의 전체 영역 판독은 제품의 같은 검출기를 사용하는 인식기 교체와 다르며, 표/경고 위치/제품 통합 정확도를 검증하지 않았다. 실험용 모델·portable 실행기는 `output/screen_text_lab/new-models-20261011/`, 수동 실행 코드·원 응답·HTML은 `output/harness/20261011-133348-b70eeeeb66/`에만 있고 통상 테스트·빌드에는 연결하지 않았다.

위 새 모델 비교를 마친 시점에는 현재 소형 한국어 모델의 추가 학습을 시도하지 않았다. 이후 사용자가 [에이전트 실행 계획](work/2026-10-11-screen-text-finetuning-plan.md)을 승인해 별도 환경·업무 자료·평가 도구·시험 학습에 착수했다. 실제 성공/실패와 적용 판단은 [실행 기록](work/2026-10-11-screen-text-finetuning-implementation.md)에 남긴다. 이 비교 종료를 개선 불가능으로 해석하지 않는다.

1차 추가 학습은 실제 GPU 학습 5회까지 완료했다. BN 통계를 고정한 B 후보는 합성 선택 100줄의 공백 제외 오류를 57→32로 줄였지만 `ppm→pp` 등의 새 오독과 기존 메모장 회귀 악화로 채택하지 않았다. 새 실제 업무 앱 자료·사람 검토·독립 final은 미완료다. 자료 다양성과 새 기호의 학습 문맥을 보강하는 다음 단계가 필요하며 제품 모델은 유지한다. 도구의 전체 자동 검사 2,404개 통과와 모델 품질 실패는 별개 결과다.

학습용 자료는 기존 dev/holdout corpus와 분리한 `tools.screen_text_lab.datasets`의 train/selection/final manifest를 사용한다. `python -m tools.screen_text_lab.crop_evaluation run <자료루트>/selection`은 선택 자료의 **줄 인식만** 제품 전처리·CTC·기존 경고 계산으로 측정한다. `--bundle <후보.json>`을 명시하면 `output/screen_text_lab/` 안에서 해시가 고정된 후보 ONNX/사전을 읽는다. 후보 역할은 공식 미학습 재수출 R 또는 학습 F이며 기본은 제품 P다. 제품 파일을 교체하지 않는다. 각각의 실행은 격리 AppData·소유 Windows Job·새 하네스 폴더를 사용하고 이미지/모델/입력 소스 변경을 검사한다.

후보 등록은 출처 선언만으로 허용하지 않는다. checkpoint·사전·학습/진단 결과·공식 source·변환 결과·고정 21개 tensor 증거를 연결하고, 실행 요청 및 반환 정답/군집/채점을 다시 대조한다. 검증 코드 사본은 보고서에 보존하며 재등록은 `--registration-id`로 별도 파일을 만든다. 추가학습 없이 BN 통계만 조합한 후보는 `bn_stat_combination_diagnostic`과 추가학습 0으로 구분한다.

변환 비교는 `atol=1e-4`, `rtol=1e-3`을 유지한다. 전체 tensor 일치 `passed`와 **제품이 실제 사용하는 CTC 단계만** 일치하는 `passed_product_visible`을 구분한다. 후자는 짧은 crop의 오른쪽 패딩을 제품 `_read`와 같은 `ceil(T × crop_width / batch_width)`에서 잘라 버렸을 때만 허용하고, `full_tensor_parity=false`·패딩 차이 개수·전체 수치 불일치를 보존한다. 실제 사용하는 구간의 수치 또는 어느 probe의 문자/기존 0.80 경고가 다르면 후보를 등록하지 않는다. 미학습 R_A 재현은 계속 전체 tensor 일치를 요구한다. 이 구분은 후보 연구 실행을 위한 것으로 제품 채택 판정을 대신하지 않는다.

`python -m tools.screen_text_lab.full_candidate run --bundle <후보.json>`은 고정된 기존 공개 dev48 실행 사본만 읽어 제품 검출→인식→배치 경로를 비교한다. CLI 형식의 시험 문구 24개를 메모장에서 두 배율로 캡처한 자료이며 실제 터미널 캡처나 표 정답은 없다. 원본 corpus·보류/최종 자료를 열지 않고, 이번 한글/PDF/Word/표 목표의 독립 최종 평가로 쓰지 않는다.

줄 crop 결과는 검출·표의 행/열·전체 화면·제품 속도 검증을 대신하지 않는다. 단일 실행 시간에는 다른 개발 작업의 영향도 포함될 수 있어 채택 성능 근거로 쓰지 않는다. `tools.screen_text_lab.evaluation`은 저장된 P/R/F 결과를 다시 채점하며, 빠진 사례·새 오류·숫자/단위·표·경고·독립 자료·성능 근거를 각각 검사한다. 합성 줄 결과만으로 제품 채택을 통과시키지 않는다. 실제 학습/모델 평가 명령은 일반 quick/full/build에서 자동 실행하지 않는다.
