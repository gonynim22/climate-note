# 화면 글자 따기 계약

다섯 번째 미니앱이며 **걷어낼 수 있는 선택형 앱**이다. 설계는 [설계 문서](superpowers/specs/2026-10-08-screen-text-capture-design.md), 최초 구현·검증은 [작업 기록](work/2026-10-08-screen-text-capture.md)을 따른다. v4.0은 최초 소형 모델을 유지하고 아래 줄·표 재구성을 개선한 버전이며, 현재 빌드 결과는 [v4.0 기록](work/2026-10-11-v4.0-release.md)에 남긴다.

## 동작
- 주머니 타일 → 도구 창 → [영역 고르기] → 화면이 멈추면 끌어서 선택(Esc·오른쪽 클릭 취소, 시작한 화면 안으로 제한) → 같은 창에 결과.
- 탭 [글자]/[표 모양]. 표가 감지되면 표 모양이 기본이다. 표 모양 복사는 탭 구분 글자와 HTML 표를 함께 넣고, 글자 복사는 일반 텍스트만 넣는다.
- 표 탭을 고치면 아직 손대지 않은 글자 탭이 다시 만들어진다. 글자 탭에서 고친 내용은 표 탭에 반영하지 않는다.
- 불확실한 곳은 노랗게 표시만 하고 자동으로 고치지 않는다. 판독 글자는 바꾸지 않는다. 예외는 넷뿐이고 모두 화면 모양을 읽는 것이다: (1) 줄 맨 앞에서 화면의 글머리 기호 모양(`■ □ ◇ ㅇ ○ -`)이 분명히 보일 때 그 자리를 기호로 붙이거나(모델이 건너뜀) 닮은 글자(`0 o O` 등)를 기호로 교체한다(엔진 절의 글머리 기호 복원). (2) 모델이 `[ ]`로 읽은 글자의 화면 모양이 낫표일 때 `「 」`로 바꾼다(엔진 절의 낫표 복원). (3) 모델이 건너뛴 줄 안 체크박스(`□ ■`)를 그 자리에 끼워 넣는다(엔진 절의 체크박스 복원). (4) 모델이 건너뛰거나 닮은 글자(`스 ㅅ ! ∆`)로 읽은 삼각형을 `△ ▲`로 넣거나 바꾼다(엔진 절의 삼각형 복원).
- 다시 고르기를 취소하거나 새 인식이 비었거나 실패하거나 캡처가 막히면 이전 결과(고친 내용 포함)와 미리보기를 그대로 둔다. 이전 결과가 있으면 결과 화면에 안내 줄만 띄우고, 없으면 처음 화면에 안내한다. 모델 오류는 [영역 고르기]·[다시 고르기]를 모두 막는다.
- 좁은 표에 맞추려고 채운 빈 칸은 읽기 전용이다.
- 사용법 안내(v3.9a): 처음 화면에는 [영역 고르기] 아래에 벡터 애니메이션(영역 고르기 → 글자 읽기 → 표로 붙여넣기, 6초 되풀이)과 팁 두 줄을 둔다. 결과 화면의 [사용법]은 같은 애니메이션이 있는 사용 방법 화면을 열고 [돌아가기]는 결과를 다시 채우지 않고 그대로(고친 글자·표·탭·상태) 돌려놓는다. 애니메이션은 그림 파일 없이 QPainter로 그리며 화면에 보일 때만 돌고(숨기면 멈춘다), 누르면 처음부터 다시 보여 준다. 새 설정 키·파일·네트워크를 쓰지 않는다.

## 줄·표 재구성
- **줄**: 상자 중심 y로 정렬하고, 세로 겹침이 작은 쪽 높이의 50% 이상이면 우선 같은 행으로 묶는다. 이 행을 중심/높이 중앙값으로 나눈 물리 줄 사이에 독립적인 열 대응이 2개 이상 반복되면 분리하여 병합 라벨이 다음 숫자 행을 흡수하지 않게 한다. 한 열의 여러 줄만으로는 행을 쪼개지 않는다. 한 셀 안의 글자는 물리 줄 순서(위→아래, 줄 안 왼쪽→오른쪽)를 따른다.
- **표 규칙**: 2칸 이상인 줄 2개 이상·열 띠 2개 이상을 사용한다. 겹쳐 이어진 문장 조각만으로 새 표를 시작하지 않는다. 작은 x 구간의 절반 이상 겹치는 열을 우선 대응시키고, 강한 대응이 없으면 기존의 실제 겹침을 쓴다. 강한 대응 옆의 작은 접촉 때문에 표를 끊거나 열을 합치지 않는다. 한 구간이 여러 열에 대응하면 표를 끝낸다. 한 열 안에 완전히 들어가고 서로 겹치는 판독 조각은 같은 셀로 모으며, 그 밖의 한 열→여러 구간 대응은 표를 끝낸다.
- **병합 머리글**: 본문에 더 많은 칸이 있는 줄이 있고, 머리글 상자의 위치/폭이 본문 열 묶음의 중앙과 열 사이 경계에 맞을 때만 묶음 첫 칸에 넣는다. 본문에서 먼저 열을 확인해 머리글 자체가 가짜 열을 만들지 않게 한다. 별도 머리글을 표에 붙일 때는 본문과의 간격도 상자 높이 이내인지 확인한다. 병합 범위를 표시하는 rowspan/colspan이나 표 선 검출은 쓰지 않으며 덮인 칸은 빈칸으로 둔다. 글자·점수·상자는 수정하지 않는다. 구현/검증은 [표 구성 기록](work/2026-10-11-screen-text-table-layout.md)을 따른다.
- **숫자 열**: 열의 비어 있지 않은 칸 중 절반 이상이 "숫자 같은" 칸이면 숫자 열이다. 분류에만 `l I → 1`, `O o → 0`, `S → 5`, `B → 8`로 닮은 글자를 바꿔 본다.
- **불확실 표시**: (1) 인식 점수가 0.80 미만인 상자, (2) 숫자 열에서 숫자 같으면서 숫자를 포함하고 닮은 영문자도 포함한 칸, (3) 모양으로 알아본 고리 모양 글머리 기호(`ㅇ`·`○`)의 **그 한 글자만**(`TextBox.unsure_prefix`→`Cell.unsure_prefix`). (1)·(2)는 칸 전체, (3)은 글자 탭에서 기호 한 글자만 노랗게 하고 표 탭에서는 그 칸을 노랗게 한다. 표시만 하며 글자는 그대로 둔다. 칸 전체 표시가 있으면 그것이 우선한다.
- 글자 탭의 불확실 표시는 칸마다 따로 위치 커서로 추적한다. 칸 끝에서 공백·마침표·Enter를 입력해도 표시 범위는 늘지 않으며, 칸의 글자를 실제로 고쳐야 표시가 풀린다.

## 엔진
- v4.3 자원 제한: 인식용 상자는 최대 512개, 높이 48px로 환산한 폭은 최대 4096px, 배치의 `최대 폭 × 상자 수`는 8192 이하(상자 수 최대 6)다. 모든 crop을 먼저 만들지 않고 현재 배치만 변환한다. 상한 초과 시 문장을 압축하거나 일부만 성공 처리하지 않고 영역을 나눠 선택하도록 안내하며 이전 결과를 보존한다. 모델 생성 전·검출 전·연결요소 행 처리·인식 배치 사이에 취소를 확인한다. 이미 실행 중인 ONNX 호출을 강제 중단하지는 않는다. 모델/사전/해시는 변경하지 않는다.
- 모델·사전·런타임 고지 목록은 `screen_text/licenses/components.json`에 두고 설정 → 라이선스에서 원문을 읽는다. PaddleOCR 원저작권을 보존한 `models/LICENSE`, 원 모델/변환본/고정 리비전/변경 여부를 구분한 `licenses/MODEL-ATTRIBUTION.txt`, ONNX Runtime/NumPy 원문을 함께 번들한다. 폴더가 없으면 목록과 원문도 함께 제외한다. 고지 정비로 모델·사전·MANIFEST 해시나 인식 동작을 바꾸지 않는다.
- PP-OCRv3 mobile det + korean PP-OCRv5 mobile rec ONNX(Apache-2.0), onnxruntime CPU, numpy만 사용한다. 모델은 `screen_text/models/MANIFEST.json`의 크기·SHA-256이 맞을 때만 불러온다.
- 2026-10-11 사용자 결정: 검증한 표 구성 개선을 적용하고 현재 소형 인식 모델을 유지한다. 추가 학습 후보는 실제 자료의 새 오독으로 미채택했으며 추가 학습을 보류한다. 실험 도구·자료·후보 모델은 제품에 포함하지 않는다. 적용/EXE 검증은 [빌드 기록](work/2026-10-11-screen-text-table-build.md), 미채택 근거는 [학습 기록](work/2026-10-11-screen-text-diverse-training.md)을 따른다.
- **공백 복원**(2026-11-06): 인식 모델은 CJK 문장에서 공백을 거의 내지 않는다(실제 공문서 PDF holdout에서 공백만 보정해도 정답 단어 일치율이 17.6%p 올랐다). 인식용 상자마다 그 크롭의 글자 픽셀(배경 중앙값과 24 이상, 가장 진한 차이의 30% 이상 다른 픽셀)을 찾아, 글자 높이의 0.40배(최소 3px) 이상 빈 열이 이어지는 틈의 가운데를 단어 경계로 본다. 그 틈을 인식 글자의 CTC 위치에 대응시켜 틈 왼쪽 글자 뒤에 공백만 넣는다(`engine.ink_gap_cuts`·`ctc_decode_detail`·`insert_gap_spaces`). 첫 글자 앞·마지막 글자 뒤의 틈, 모델이 이미 공백을 낸 자리, 같은 자리의 중복 틈에는 넣지 않는다. 글자는 바꾸거나 추정하지 않고 화면에 실제로 있는 틈만 잰다. 구간별로 다시 읽는 방식은 글자 오류가 늘어 쓰지 않았다. `ctc_decode`는 진단 도구가 가로채는 지점이라 상자마다 한 번 그대로 부르고, 디코드 결과와 위치용 분해의 글자가 같을 때만 공백을 넣는다. 모델·사전·MANIFEST 해시, 상자 상한, 점수·불확실 표시는 바꾸지 않는다. 근거와 수치는 [실패 분석 기록](work/2026-11-05-screen-text-failure-analysis.md)·[적용 기록](work/2026-11-06-screen-text-space-restore.md)을 따른다.
- **글머리 기호 복원**(2026-11-06, `screen_text/leading_symbols.py`): 모델은 공문서의 글머리 기호를 거의 읽지 못한다. 인식 상자의 왼쪽(상자 높이의 2.5배까지, 같은 줄의 왼쪽 이웃 상자 전까지)과 상자 안 앞부분(상자 높이의 4배까지)에서 글자 픽셀을 덩어리로 나눠, 표 테두리·괄호처럼 가늘고 긴 덩어리(가로/세로 0.4 미만, 높이 0.6 이상)는 건너뛴 첫 덩어리를 본다. 3px 이상이고 뒤 글자와 폭의 절반(최소 3px) 이상 떨어져 있을 때만 기호 후보이며 모양으로 분류한다: 속이 찬 정사각 `■`, 속이 빈 정사각(네 꼭짓점 칸(폭·높이의 10%) 중 3곳 이상이 찬 경우) `□`, 네 모서리가 비고 높이 0.5 이상인 마름모 `◇`, 그 밖의 고리는 줄 글자 높이의 0.72배 이상이면 `○`, 아니면 `ㅇ`. 짧고 납작한 막대는 3px 조건과 별도로 `-`로 본다: 길이가 줄 글자 높이의 0.15~0.6배이고 굵기의 2배 이상, 굵기는 0.22배 이하, 막대 가운데가 줄의 0.4~0.72 자리, 뒤 글자와 길이의 0.75배(최소 3px) 이상 떨어진 경우다. 모델이 그 자리를 이미 `- – — ~` 등으로 읽었으면 판독을 그대로 둔다. 모델이 상자 안에서 그 자리를 `0 o O C c D . : - · □ ■ ▪ ○ ● ㅁ ㅇ` 중 하나로 읽었으면 그 한 글자를 교체하고, 읽지 않았거나(`□`는 상자가 기호 오른쪽에서 시작해 대부분 상자 밖이다) 다른 글자면 앞에 `기호 + 공백`을 붙인다. 글자 판독은 바꾸지 않는다. `■ □ ◇ -`는 모양이 분명해 표시하지 않고, 고리는 `ㅇ ◦ ○ o`를 모양으로 다 구별할 수 없어 크기에 따라 `ㅇ`·`○`로 내되 그 한 글자만 확인 필요로 표시한다(사용자 결정 2026-11-06: 그대로 내지 않고 표시). `■`와 `▪`는 구별하지 않고 `■`로 낸다. `recognize()`가 `_read` 뒤에 한 번 적용하므로 진단 도구의 후보도 같이 적용된다. 근거와 수치는 [기호 시험 기록](work/2026-11-06-screen-text-bullet-spike.md)·[적용 기록](work/2026-11-06-screen-text-bullet-symbols.md)을 따른다.
- **낫표 복원**(2026-11-06, `screen_text/corner_brackets.py`): 모델 사전에 `「 」`가 없어 공문서의 법령명 표기가 `[ ]`로 읽힌다. `_read`가 공백을 넣기 전에 `[`·`]` 조각의 CTC 위치 근처 글자 덩어리(8방향 연결, 줄 글자 높이의 절반까지)를 보고, 줄 글자 높이의 0.72배 이하이고 위(「) 또는 아래(」)에 붙어 반대쪽이 0.3배 이상 비었으며 꺾임이 하나뿐일 때(가로획은 한쪽만, 세로획이 높이의 0.7 이상, 맞은편 사분면이 빔)만 `「`·`」`로 바꾼다. 모델이 읽은 방향을 뒤집지 않고 위치도 그대로 둔다. 모양이 분명할 때만 바꾸므로 확인 필요 표시는 붙이지 않는다. 큰 제목 글꼴의 긴 낫표는 진짜 `[ ]`와 헷갈려 `[ ]`로 둔다. 모델이 아예 읽지 않은 낫표는 복원하지 않는다. `ctc_decode` 호출 구조는 그대로다. 근거와 수치는 [적용 기록](work/2026-11-06-screen-text-corner-brackets.md)을 따른다.
- **체크박스 복원**(2026-11-06, `screen_text/leading_symbols.py`): 양식의 `□ 특별시 ■ 광역시 □ 도`, `□ 동의 □ 동의하지 않음`에서 체크박스가 사라지면 어느 항목에 표시됐는지 알 수 없다. 원인이 둘이라 두 곳에서 막는다. (1) 위치 찾기가 체크박스만 든 작은 상자를 만들고 모델이 빈 글자로 읽는 경우: 빈 글자로 읽힌 상자는 글머리 기호 탐색의 왼쪽 경계에서 빼서, 오른쪽 글자 상자가 정상 높이로 기호를 찾는다. 빈 상자 자체에서 기호를 내지 않는다. 그 상자는 기호의 속이나 일부만 잘린 경우가 있어 모양을 믿을 수 없다. (2) 한 상자 안의 체크박스를 모델이 건너뛴 경우(`restore_inline_checkboxes`): `_read`가 공백을 넣기 전에 상자의 글자 덩어리를 보고, 높이가 6px 이상이고 줄 글자 높이의 0.6배 이상이며 양옆이 폭의 절반(최소 3px) 이상 비고 `■`·`□`로 분류되며 그 자리(앞뒤 CTC 한 단계)에 모델이 낸 글자가 없을 때만 끼워 넣는다. 표 세로선을 뺀 첫 덩어리는 줄 맨 앞이라 글머리 기호 규칙이 맡는다(두 규칙이 같은 기호를 두 번 내지 않게 한다). `동의 □`처럼 항목 뒤에 오는 경우가 있어 마지막 글자 뒤도 본다. 모델이 그 자리에 글자를 냈으면 건드리지 않는다. 모양이 분명할 때만 넣으므로 확인 필요 표시는 붙이지 않는다. 근거와 수치는 [적용 기록](work/2026-11-06-screen-text-form-checkboxes.md)을 따른다.
- **삼각형 복원**(2026-11-06, `screen_text/triangles.py`): 모델 사전에 `△ ▲`가 없어 `△32%`가 `32%`로 읽혀 감소가 증가로 바뀐다. `_read`가 공백을 넣기 전에 두 경우를 본다. (1) 모델이 닮은 글자 `스 ㅅ ! ∆`로 읽은 자리: 그 열의 글자 덩어리(8방향 연결)가 삼각형이면 같은 위치에서 바꾼다. `∆`(U+2206)는 뜻이 살아 있지만 공문서 문자집합에 없어 찾기에 걸리지 않고 같은 표에서 `△`와 섞이므로 통일한다. (2) 이웃한 CTC 글자가 줄 글자 높이의 1.2배 이상 떨어지고 그 사이에 글자 픽셀이 있는 자리: 덩어리가 삼각형이면 끼워 넣는다(단어 사이 빈칸은 덩어리를 추적하지 않는다). 삼각형은 높이 6px 이상, 줄 글자 높이의 0.45배 이상, 가로/세로 0.85~1.75, 빈 행 없음, 위쪽 20% 폭이 전체의 0.4배 이하이고 가운데에 있음, 맨 아래 행 폭 0.7배 이상, 행 폭이 곧은 빗변에서 0.3배 이내일 때다. 100% 배율에서는 가는 밑변이 옅어 글자 픽셀로 잡히지 않기도 하므로 밑변을 요구하지 않고 두 다리 끝의 벌어짐을 본다. 구간(높이 30~80%)의 모든 행이 0.9 이상 차면 `▲`, 0.75 이하면 `△`다. 덩어리가 차지한 열에 다른 글자 픽셀이 10%를 넘으면 버린다(`스`의 `ㅡ`). 그 자리에 모델이 낸 다른 글자가 있으면 건드리지 않는다. `△32%`처럼 밑변이 뒤 숫자에 붙은 덩어리는 자르는 열을 옮겨 가며 `△`를 찾는다. 이 자르기는 `△`에만 쓴다. 잘라 낸 `▲`는 실측에서 모두 잘린 큰 제목의 글자 획이었고, 진짜 `▲`는 목록 표시라 뒤 글자에 붙지 않는다. `A`는 굵은 제목 글씨가 꽉 찬 삼각형처럼 보여 닮은 글자에 넣지 않는다. 확인 필요 표시는 붙이지 않는다. 근거와 수치는 [적용 기록](work/2026-11-06-screen-text-triangles.md)을 따른다.
- 엔진은 처음 인식할 때 작업 스레드에서 불러오고, 사용자가 창을 닫거나 초기화·종료하면 내린다. 첫 불러오기 중에 창을 닫으면 모델을 보관하지 않는다. 텔레메트리를 끈다. 네트워크를 쓰지 않는다.
- 엔진 모듈을 불러오지 못하면 "모델" 오류로 안내한다.

## 데이터와 보안
- 찍은 화면 전체는 선택·취소 즉시 버린다. 잘라낸 영역과 결과는 메모리에만 두며 임시 파일을 만들지 않는다. 로그에는 오류 종류만 남긴다.
- DB v17·Export v2·salt·설정 키·바로가기 6슬롯을 바꾸지 않는다. 새 설정 키를 만들지 않는다.
- 캡처가 막히면(거의 검은 화면) 안내만 하고 우회하지 않는다. 못 찍었거나 막힌 화면에는 오버레이를 띄우지 않고, 남는 화면이 없으면 막힘으로 안내한다. 빈 영역은 취소처럼 처리한다.

## 수명 처리
- 공용 연결부(`optional_mini_apps.py` → `ui_main` 선택형 미니앱 메서드)를 따른다. 연결 지점은 10곳(열기, 사이드바 숨김, 크기 변경, 데이터 초기화 전, 초기화 성공, 트레이 숨김, 종료, 화면 변경, 잠금, 메인 창 Hide 이벤트)이다.
- 잠금: 취소·숨김·비활성(결과 유지). 트레이·사이드바·크기 변경·초기화 전·메인 창 숨김: 취소·숨김. 화면 변경: 오버레이 닫기·화면 맞춤(`hide_owned_popups(restore=True)`). 영역 고르기 대기·선택 중이었으면 숨겨 둔 도구 창을 바뀐 화면에 맞춰 취소처럼 다시 보인다(결과 유지, v4.4b). 숨김·잠금 경로는 `restore`를 쓰지 않으며 비활성 창은 다시 보이지 않는다. 초기화 성공·종료: `shutdown()` 후 폐기.

## 개발용 정확도 진단 도구

별도 개발 도구 `tools/screen_text_lab/`는 [개발 계획](work/2026-10-10-screen-text-lab-plan.md)의 자료 검증·채점·제품 기준 실행·오프라인 HTML 비교와 조건별 합성 자료·후보 비교·주석 영역 직접 인식 진단을 제공한다. [사용법과 현재 범위](SCREEN_TEXT_LAB.md)를 따른다. 2026-10-11 합성 1,920개 dev/480개 최종 평가에서 선택적 재인식 후보는 전체 글자 오류를 일부 줄였지만 완전 일치·표의 채택 기준에 미달해 제품에 적용하지 않았다([평가 기록](work/2026-10-10-screen-text-accuracy-improvement.md)). 원본 1,000개 확대·실제 업무 캡처와 혼합 DPI·새 원문 최종 평가 집합은 후속 범위다. 대규모 진단은 명시적인 별도 명령으로만 실행하고 일반 테스트/빌드/앱 시작에 연결하지 않는다. 가벼운 자체 검사와 기존 소규모 모델 회귀의 경계는 [검증 지침](TESTING.md)을 따른다.

개발용으로 생성하거나 등록한 시험 자료만 별도 출력 폴더에 보존한다. 제품의 캡처 이미지 메모리 전용·로그 본문 미저장·오프라인·자동 글자 교정 금지 계약은 그대로 유지한다.

모델 출력·CTC 진단(`run --diagnose-ctc`)도 수동 개발 도구다. 기존 합성 선택 표본 76개의 [원인 진단](work/2026-10-11-screen-text-ctc-diagnosis.md)에서 반복/blank 처리와 독립 계산이 일치했고 출력 절삭을 해제해도 문자열이 같았다. 디코딩만 바꾼 가상 비교는 일부 오류만 줄였으며 제품에는 적용하지 않았다. 실제 캡처·새 원문 독립 평가는 별도 후속 범위다.

입력/모델 비교(`run --recognizer ... --input-profile ...`)는 [사용법](SCREEN_TEXT_LAB.md)의 수동 개발 도구로만 제공한다. 2026-10-11 개발용 1,920개에서 대체 한국어 v3/EasyOCR g2는 현재 모델보다 오류가 많았고, 입력 정규화는 기존 개선 효과를 재현했지만 신규 오류/표 퇴행으로 적용하지 않았다([비교 기록](work/2026-10-11-screen-text-model-input-comparison.md)). 외부 모델은 개발 출력 폴더에서 해시 검증 후 오프라인으로만 실행하며 번들·제품 의존성을 변경하지 않는다. 결과 불일치 경고의 모의 분석은 제품 동작/정확도 개선으로 적용한 결과가 아니다.

두 판독이 다른 글자/삽입점을 표시하는 후속은 개발용 `disagreement`·`benchmark-disagreement` 명령으로만 진단한다. 화면 전체 경고와 실제 표시 위치 적중·정렬 모호성·추가 시간을 구분하며, 제품 원문/경고 UI/복사에는 적용하지 않았다. [사용법](SCREEN_TEXT_LAB.md)과 [진단 기록](work/2026-10-11-screen-text-disagreement-warning.md)을 따른다.

불일치 경고의 문자 점수/차이/누락 조건 비교도 `warning-rules` 수동 진단에 한정한다. 기존 원문과 경고를 유지하며 조정용에서 조건을 고정한 뒤 확인용의 오경고와 놓친 오류를 함께 평가한다. 기존 dev의 재분할은 새 독립 검증이 아니다. [조건 비교 기록](work/2026-10-11-screen-text-warning-rules.md)에 증거를 남기며 제품 UI에는 아직 적용하지 않았다.

## 알려진 한계
- 띄어쓰기는 이미지의 틈으로 복원하지만 완전하지 않다. 소형 모델 자체는 마침표·쌍점 뒤와 어절 사이의 공백을 거의 내지 않아(예: `2026. 7. 1.` → `2026.7.1.`) 틈 기준으로 보충한다. 글자 높이 0.40배보다 좁게 붙어 있는 틈은 놓치고(자간이 좁은 한컴 글꼴 등), 자간이 넓은 글꼴에서는 한글 음절 사이에 공백이 끼어들 수 있다. 사용자가 확인해야 한다.
- 공백 복원의 측정(2026-11-06, 실제 공개 문서 PDF 533쪽에서 만든 holdout 600장, 화면 배율 100/150/200%): 정답 단어가 그대로 나온 비율 64.8% → 82.4%, 글자 오류는 변화 없음. 잡음·JPEG 35·번짐+기울임 스캔 느낌 이미지에서도 각각 +18~+38%p. 실제 한글(HWP)·엑셀·ClearType 화면은 미측정이다.
- 글머리 기호 복원의 측정(2026-11-06, 같은 PDF의 **앞선 평가에 쓰지 않은 48쪽 576장**, 화면 배율 100/150/200%, 임계값을 정한 뒤 한 번 평가): 못 읽는 비율이 `□` 100% → 10%, `ㅇ` 52% → 6%(`■`는 12개뿐이라 판단 보류, 앞선 자료 152개에서 97% → 18%)로 줄었고 판독 글자 누락·오독이 3.18% → 2.81%(공백 복원과 별개로 관대 채점), 한두 줄 선택의 완전 일치 21 → 67/192(공백 복원 포함, 공백만 57)였다. 잘못 더해진 기호는 `□` 24·`ㅇ` 21·`■` 5개이며 대부분 정답 글자 레이어가 `◦ o ◇` 같은 닮은 기호를 쓴 줄이다. `ㅇ`로 낸 줄 중 실제 `□`는 8줄이고 이들은 확인 필요 표시가 붙는다. 고리 표시(확인 필요)는 이 PDF에서 쪽 전체 100% 기준 쪽당 평균 3.2개·중앙값 3개·최대 9개였고 48쪽 중 11쪽은 0개였다(`ㅇ` 개조식 쪽이 많을수록 늘어난다).
- 글머리 기호의 남은 한계: `ㅇ ◦ ○ o`와 `■ ▪`는 모양으로 구별할 수 없고, 같은 줄에 이어 붙은 둘째 항목의 기호와 표 칸 첫머리는 이웃 상자 경계에 의존하며, 마름모(`◇`)가 `□`로 나오는 경우가 있다(드물다). `Ⅳ Ⅴ Ⅰ`와 `⇒`는 사전에 있어도 `IV V I`로 읽히거나 거의 읽히지 않고, 미해결 과제다. `△ ▲`는 삼각형 복원으로 대부분 살아났으나 `▲`는 절반쯤 남았다(엔진 절).
- 낫표 복원의 측정(2026-11-06, 같은 PDF에서 규칙을 정할 때 쓰지 않은 76쪽 912장, 화면 배율 100/150/200%): `「 」` 238개 중 못 읽는 수가 238 → 73으로 줄었다(복원율 100% 배율 52%, 150% 81%, 200% 85%). 정답에 있는 진짜 `[ ]` 70개 중 낫표로 잘못 바뀐 것은 없고, 잘못 더해진 `[ ]`는 228 → 64개다. 판독 글자 누락·오독은 두 묶음에서 2.49% → 2.41%, 2.81% → 2.73%(관대 채점)다. 남은 낫표의 대부분은 모델이 아예 읽지 않은 경우이며 복원 대상이 아니다.
- 큰 고리 수정의 측정(2026-11-06): 사용자가 만든 양식이 다른 문서 11쪽 132장에서 `○`가 전부 `□`로 나오던 것을 꼭짓점 기준으로 고쳤다. `○` 173개 중 못 읽음 173 → 47(이 중 36개는 `ㅇ`로 나오며 확인 필요 표시가 붙는다), 잘못 더해진 `□` 134 → 5, 판독 글자 누락·오독 3.41% → 2.92%, 정답 단어 일치율 89.6% → 91.1%(관대 채점, 규칙을 정한 자료). 규칙을 정할 때 쓰지 않은 앞의 PDF 912장에서는 잘못 더해진 `□` 29 → 6이고 글자 오류는 2.36% → 2.35%, 2.71% → 2.69%로 나빠지지 않았다.
- 줄 맨 앞 `-` 복원의 측정(2026-11-06, 같은 PDF에서 규칙을 정할 때 쓰지 않은 76쪽 912장): 줄 맨 앞 `-` 739개 중 사라진 수가 68 → 20으로 줄었다. 새로 붙은 51줄은 모두 정답과 맞았다. 판독 글자 누락·오독은 두 묶음에서 2.41% → 2.36%, 2.73% → 2.71%(관대 채점)다.
- 작은 문장부호의 남은 한계(2026-11-06): 100% 배율에서 낱말 뒤 `*`는 47%, 가운뎃점은 83%, 연도 `'24`는 88%만 맞고 150% 이상에서는 나아진다. 모델이 건너뛴 작은 기호를 덩어리로 찾아 넣는 방식은 `비'전`, `비·용`처럼 없는 기호가 글자 사이에 들어가 쓰지 않았고, `"`→`*` 교체도 증거가 부족해 쓰지 않았다([기록](work/2026-11-06-screen-text-leading-dash.md)).
- 합성 표본 측정(개발 PC, 공백을 무시한 글자 정확도, 공백 복원 적용 전): 소형 모델 0.996, Windows 내장 OCR 0.575. 공백까지 따지면 전체 0.940, 본문만 0.887이다. 표 칸은 따로 나뉘어 공백 영향이 적다. Windows OCR의 0.575에는 표를 열 단위로 내보내는 읽기 순서 불이익이 들어 있다. 순서를 무시하면 약 0.68이고 남은 차이는 누락된 칸이다.
- 인식 시간은 3~5줄 표본에서 최대 0.23초, 24~48줄 영역에서 약 1.3~1.4초였다. 페이지 크기 영역의 시간은 업무 PC에서 따로 본다.
- 큰 영역은 느리고 덜 정확하다(개발 PC, 실제 모델, 합성 표본). 1920×1080·2560×1440의 13~16px 글자는 공백을 무시하고 100% 맞았고 2.2~3.4초였다. 3840×2160의 16px 글자는 상자 990개(정답 840개), 정확 일치 49%, 6.5초였다. 위치 찾기가 긴 변을 960px로 줄여서 하기 때문이다. 4K·전체 화면보다 필요한 영역만 골라 읽는다.
- 병합 셀의 범위를 항상 복원하지는 못한다. 여러 줄 머리글·행을 가로지르는 단위 표기·비어 있는 일정 열은 여전히 잘못 나뉠 수 있다. 못 읽은 기호나 빈 행을 추정해 넣지 않는다. 많이 기울어진 스캔본은 지원하지 않는다.
- 글자 탭의 불확실 표시: 실행 취소(Ctrl+Z)는 풀린 표시를 항상 되살리지는 않는다(일부 글자만 고친 뒤 되돌리면 글자는 돌아와도 표시는 풀린 채 남는다).
- 합성 표본 기준이라 실제 스캔 문서의 성능, 보안 프로그램의 캡처 차단, 한글 표 붙여넣기, 혼합 DPI는 업무 PC에서 확인한다.
